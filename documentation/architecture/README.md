# Общая архитектура

Эта страница объясняет устройство AzurPilotRu на уровне системы. Для понимания не требуется читать Python-код.

В упрощённом виде проект состоит из пяти слоёв:

```text
Пользователь
   │
   ▼
WebUI / CLI
   │
   ▼
Планировщик и прикладные сервисы
   │
   ├──► Game runtime ─► ADB / эмулятор ─► Azur Lane
   │
   ├──► PostgreSQL
   ├──► Redis
   └──► Observability / MCP / внешние интеграции
```

## Пользовательский слой

Пользователь взаимодействует с проектом двумя основными способами:

- **WebUI** — настройка профилей и игровых задач;
- **`azur` CLI** — установка, запуск, остановка, диагностика, восстановление и обновление.

Эти интерфейсы не должны владеть бизнес-логикой по отдельности: они вызывают общие сервисные границы.

## Профиль и планировщик

Профиль содержит пользовательскую конфигурацию.

Планировщик:

- определяет включённые задачи;
- учитывает `NextRun`;
- применяет приоритеты;
- передаёт управление готовой задаче;
- получает от неё новое время запуска или результат завершения.

Профиль — это конфигурация. Активная runtime-задача — отдельное фактическое состояние.

## Игровой runtime

Игровая задача работает циклически:

```text
снимок экрана
→ распознавание состояния
→ выбор одного допустимого действия
→ ввод/клик
→ новый снимок экрана
```

Такой цикл позволяет принимать решение по фактическому интерфейсу игры, а не выполнять заранее записанную последовательность кликов без проверки.

Подробнее: [Как AzurPilotRu управляет игрой](game-control-loop.md).

## Прикладной слой

Между UI/MCP и legacy runtime развивается нейтральный application layer.

Он предоставляет typed operations для:

- профилей;
- статусов;
- каталога задач;
- Fleet State;
- morale;
- storage.

Транспортный код не должен отдавать наружу внутренние `ProcessManager`, raw config dictionaries, device objects или DB-specific exceptions.

## Хранилище

Текущая production-модель:

- **PostgreSQL** — durable source of truth для доменных данных;
- **Redis** — reconstructable runtime cache.

Redis не является fallback-хранилищем PostgreSQL.

Подробнее: [Хранение данных](storage.md).

## Инфраструктура

Docker Compose управляет локальными infrastructure services:

- PostgreSQL;
- Redis;
- pgAdmin;
- RedisInsight;
- Grafana;
- Loki;
- Prometheus;
- Tempo;
- Alloy;
- опциональным Caddy.

Подробнее: [Docker-инфраструктура](docker.md).

## MCP

Проект содержит два first-party MCP:

- **Dev MCP** — разработка, smoke и контролируемые development sessions;
- **Game MCP** — чтение/управление пользовательским игровым runtime в рамках отдельного контракта.

Они не являются одним универсальным gateway.

Подробнее: [MCP](mcp.md).

## Observability

Логи, метрики и трассировки могут поступать в локальный observability-контур.

Но telemetry не является доказательством текущего execution state: authoritative runtime состояние читается через собственные runtime/application boundaries.

Подробнее: [Наблюдаемость](observability.md).

## Главный принцип архитектуры

AzurPilotRu старается разделять:

- конфигурацию и фактическое runtime-состояние;
- durable данные и cache;
- пользовательский lifecycle и developer tooling;
- локальные first-party surfaces и внешние интеграции;
- read-only наблюдение и mutating operation.

Это делает ошибку более локальной: проблема Redis не должна превращаться в потерю PostgreSQL, а проблема observability — останавливать игровой logger.
