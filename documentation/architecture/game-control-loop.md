# Как AzurPilotRu управляет игрой

AzurPilotRu не исполняет одну длинную запись координат кликов. Основная модель управления — **state loop**.

```text
снимок
  ↓
распознавание
  ↓
понимание текущего экрана
  ↓
одно допустимое действие
  ↓
новый снимок
```

## 1. Получение изображения

Device layer получает свежий screenshot Android runtime.

Метод зависит от настройки:

- ADB;
- uiautomator2;
- aScreenCap;
- DroidCast;
- MuMu/Nemu IPC;
- другие поддерживаемые backend.

Для пользователя предпочтителен `ScreenshotMethod: auto`, пока нет конкретной причины менять backend.

## 2. Распознавание

AzurPilotRu использует несколько видов распознавания:

- шаблоны изображений;
- Button-объекты с областями поиска;
- OCR;
- map detection;
- специализированные игровые detectors.

Результат распознавания используется как evidence текущего состояния.

## 3. Выбор действия

Конкретная задача решает, что допустимо сделать в текущем состоянии.

Например:

- открыть карту;
- выбрать флот;
- начать бой;
- забрать награду;
- закрыть popup;
- отложить задачу;
- запросить takeover.

## 4. Одно действие

После клика/ввода проект не должен слепо считать, что интерфейс уже перешёл в ожидаемое состояние.

Следующий screenshot подтверждает фактический результат.

Это особенно важно при:

- задержках эмулятора;
- сетевой загрузке;
- случайных popup;
- игровых объявлениях;
- urgent commission;
- ошибке распознавания;
- изменившемся UI события.

## 5. Общие handlers

Повторяющиеся состояния — login, popup, комиссии, информационные окна и другие — обрабатываются общими handlers.

Они позволяют игровым задачам не дублировать одну и ту же recovery-логику.

## Ошибки и takeover

Если состояние нельзя безопасно классифицировать, правильное поведение не всегда состоит в ещё одном клике.

Некоторые ошибки:

- повторяются ограниченно;
- передаются верхнему планировщику;
- требуют restart;
- останавливают задачу;
- требуют ручного takeover.

## Почему нельзя «ускорить» всё уменьшением screenshot interval

Более частые снимки увеличивают нагрузку и не исправляют неправильную модель состояния.

В конфигурации отдельно существуют:

- обычный screenshot interval;
- combat screenshot interval;
- OCR backend/device.

Менять их следует по результатам диагностики, а не как универсальный способ ускорения.

## Практическое следствие

Если автоматизация застряла, полезный вопрос:

> «Какой экран она фактически видит и какое состояние распознала?»

а не:

> «Какой следующий клик должен был быть по сценарию?»

Именно поэтому screenshots и журналы важны при диагностике UI-задач.
