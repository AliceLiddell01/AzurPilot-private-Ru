# Документирование изменений

Публичная документация AzurPilotRu хранится в `documentation/` и публикуется через GitBook.

Она существует **для человека**, а не как расширение agent context.

## Язык

Весь пользовательский текст — на русском языке.

Не переводятся механически:

- команды;
- пути;
- API identifiers;
- package names;
- config keys;
- protocol names;
- значения, где перевод изменит машинный контракт.

## Аудитория

Исходное предположение:

> читатель впервые увидел AzurPilotRu и не обязан читать код.

Поэтому плохая документация говорит:

> «Смотрите `LifecycleService._port_state()`».

Хорошая документация объясняет:

> «Start не завершает чужой процесс, который просто занял порт WebUI».

Код — источник факта для автора документации, а не инструкция читателю.

## Не копируйте agent context

`.codex/context/` оптимизирован под coding agents:

- высокая плотность;
- contracts;
- ownership;
- routing;
- экономия context window.

GitBook оптимизирован под понимание человеком.

Эти системы могут описывать один факт, но не должны быть зеркалами друг друга.

## Не копируйте engineering docs целиком

`docs/` содержит глубокие implementation/migration документы.

В GitBook из них извлекается пользовательски полезная модель, а не весь historical design record.

## Одна страница — один информационный контракт

По заголовку должно быть понятно, зачем открывать страницу.

Не объединяйте на одной странице:

- установку;
- историю проекта;
- все CLI flags;
- архитектуру PostgreSQL;
- troubleshooting.

Но и не создавайте отдельный файл на два предложения без причины.

## Подробность без графомании

Ограничения context window здесь не диктуют длину, но текст всё равно должен быть сканируемым.

Используйте:

- короткие разделы;
- конкретные заголовки;
- таблицы для справочника;
- примеры только там, где они помогают действию;
- ссылки на отдельное объяснение вместо лекции внутри how-to.

Небольшое повторение допустимо, если оно экономит читателю лишний переход.

## Фактическая точность

Не документируйте предполагаемое поведение.

Перед добавлением утверждения найдите подтверждение в:

- production-коде;
- source configuration;
- тестах;
- актуальном engineering document, согласующемся с кодом.

Если код и старый документ расходятся, сначала установите фактическое поведение.

## Изменение поведения = изменение документации

Если PR меняет:

- установку;
- CLI;
- WebUI;
- настройку;
- task;
- stop condition;
- сетевой endpoint;
- privacy;
- supported platform/region;
- storage;
- recovery;

проверьте соответствующую GitBook-страницу.

## Навигация

Новые страницы добавляются в `documentation/SUMMARY.md`.

Файловые пути предпочтительно оставлять ASCII, а пользовательские заголовки — русскими.

После изменения проверьте, что все Markdown-ссылки разрешаются и GitBook preview проходит.
