# Журналы

AzurPilotRu показывает журнал выполнения в консоли и WebUI и одновременно поддерживает ограниченный диагностический контекст для ошибок.

Текущая runtime-система логирования намеренно отличается от старой модели «найдите огромный локальный log-файл».

## Консоль

Если WebUI запущен из терминала или foreground-режима, сообщения Rich logger выводятся в консоль.

Формат содержит время и пользовательское сообщение.

## WebUI

WebUI получает отрисованные записи журнала через runtime handler. Для обычного пользователя это основной способ наблюдать:

- какую задачу выполняет профиль;
- что распознано;
- почему задача отложилась;
- какое условие остановки сработало;
- где произошла ошибка.

## Диагностический контекст

Logger хранит bounded in-memory контекст последних событий. Текущая ёмкость — 200 записей.

Он используется для incident/error анализа без необходимости удерживать бесконечный файл журнала.

## Локальный runtime-файл

Текущий `configure_runtime_logging()` прямо фиксирует политику: обычный runtime **не создаёт отдельный локальный log-файл автоматически**.

Console/WebUI и bounded incident context доступны независимо от OTLP/observability.

В кодовой базе сохраняются legacy adapters для старых file logs, но они не должны быть основой инструкции для современной установки.

## Observability

Если инфраструктура observability настроена, structured logs могут отправляться в текущий telemetry pipeline и анализироваться через Loki/Grafana.

Ошибка необязательной observability не должна останавливать основной WebUI logger.

Подробнее: [Наблюдаемость](../architecture/observability.md).

## Ошибки и скриншоты

Настройки `Error` содержат:

- обработку ошибок;
- сохранение error evidence;
- лимит количества error logs;
- длину screenshot context.

Кроме того, `DropRecord.SaveFolder` по умолчанию указывает:

```text
./screenshots
```

DropRecord управляет отдельными снимками результатов исследований, комиссий, боя и других поддерживаемых сценариев. Это не то же самое, что общий runtime log.

## Что прикладывать при обращении за помощью

Минимально полезный набор:

1. точная команда, которой запускали AzurPilotRu;
2. профиль (только имя, если полный JSON не нужен);
3. название задачи;
4. последние релевантные сообщения WebUI/консоли;
5. screenshot проблемного игрового состояния, если он не содержит нежелательных данных;
6. вывод `azur doctor`, если проблема инфраструктурная.

## Что нельзя публиковать вслепую

Перед отправкой проверьте наличие:

- OnePush tokens;
- API keys;
- webhook URL;
- credentials PostgreSQL/Grafana;
- приватных public-host конфигураций;
- содержимого `.env`;
- полного профиля с sensitive полями.

Runtime logger санитизирует часть чувствительных traceback-полей, но это не заменяет ручную проверку того, что вы публикуете.
