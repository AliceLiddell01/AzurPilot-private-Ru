# Разработка AzurPilot

Навык направляет к владельцам правил и помогает закончить изменение в
репозитории, а не заменяет жизненный цикл Git или матрицу проверок.

## Вход и границы

1. Прочитай корневой `AGENTS.md` и `.codex/context/INDEX.md`.
2. Подтверди рабочую копию, ветку, базовый SHA и сохранность пользовательских
   изменений.
3. Открой только документы-владельцы фактической области изменений.
4. Найди владельца поведения, путь вызовов, ближайшие контрактные тесты и
   первопричину. Затем не перечитывай те же участки без нового вопроса.
5. Меняй минимальную связанную область; сначала выясни владельца набора исходников
   или сгенерированного файла и найди генератор.

## Оркестрация субагентов

- До реализации определи, есть ли независимые направления исследования.
- Если они есть, делегируй соответствующее исследование подходящим ролям
  проекта; общие изменения и интеграцию оставь корневому агенту.
- Для существенного варианта изменений организуй свежую независимую волну
  проверки, когда это оправдано классом и составом изменений.
- Подробная политика и границы ролей принадлежат
  `.codex/context/12-SUBAGENT-ORCHESTRATION.md`.

Git, ветки, PR, слияние и очистка принадлежат `.codex/context/GIT-WORKFLOW.md`.
Выбор этапов проверки, цикл исправления тестов и точка заморозки принадлежат
`.codex/context/08-VERIFICATION.md`. Инструменты Python, типизированные сервисы,
MCP и контракты публикации принадлежат `.codex/context/11-PYTHON-TOOLING.md`.
Для проверки через графический интерфейс, браузер или работающую программу
открывай только [проверку в браузере и рабочей среде](references/browser-and-live-testing.md).

## Основной порядок работы

- Изменение MCP синхронизируй после заморозки варианта изменений одним вызовом
  `azur mcp sync --base <exact-base-sha>`. `NO_CHANGES` и `SYNCED` — конечные
  результаты. При `SYNCED` уже обработаны сгенерированные метаданные, готовность
  принадлежащей проекту среды выполнения и приёмка новым клиентом. После
  изменения набора исходников MCP повтори синхронизацию: версия рассчитывается
  относительно точной базы и итогового варианта.
- Публикуй задачу одной командой `azur delivery publish --message
  "type(scope): краткое описание"`. По умолчанию команда включает все изменённые
  пути варианта, в том числе сгенерированные метаданные MCP; `--path` нужен только
  для намеренно ограниченной области. Не создавай внешний манифест публикации и
  не запускай `validate MANIFEST` перед обычной публикацией.
- Для обычной проверки используй `dev_run_smoke`: ограниченный сценарий возвращает
  конечный результат после очистки. Автоматические контрольные точки выполняются
  по декларативным условиям; ручной инструмент `checkpoint` не входит в каталог.
  Длинный интерактивный или визуальный сценарий запускай через отдельный
  публичный `dev_start_smoke`; он возвращает `DEV_SMOKE_STARTED`. Ход выполнения
  читай через `dev_get_smoke`, а визуальную оценку проводи отдельными средствами
  оценки.
- `impact`, `status`, `reconcile`, `start`, `stop`, `restart`, `accept`,
  `delivery validate`, `dev_get_smoke` и инструменты снимка экрана/оценки оставлены
  для диагностики или соответствующих асинхронных сценариев и оценки, а не как
  обязательная последовательность штатного порядка действий.

Действия оператора, принадлежащие проекту, запускай только буквальной командой
`azur ...` через PATH текущей оболочки. `uv` используй для зависимостей,
начальной настройки, тестов и сборки. Не подменяй типизированный результат
разбором текстового вывода CLI или вызовом внутренних модулей Python.

## Проверка и публикация

Повторяй конкретный упавший тест; после исправления запускай только затронутую
быструю проверку. Набор тестов подсистемы запускай после стабилизации области,
полный относящийся к задаче набор — один раз для зафиксированного варианта.
Существенное изменение кода или конфигурации после проверки делает её результат
неактуальным; правка только отчёта — нет. Используй утверждённые команды проверки
и тестирования из документов-владельцев; не запускай шумную общую команду
`ruff check .` без отдельной цели.

Проверку CodeRabbit запускай только по явному запросу пользователя или
обязательному правилу проекта; явно передай её соседнему навыку
`azurpilot-coderabbit-review`, которому принадлежат ограничения частоты,
повторов и разбора результатов. Правила для чернового PR, проверки CI на точном
коммите, передачи на финальное пользовательское ревью и запрета слияния без
отдельной текущей команды пользователя определяет `GIT-WORKFLOW.md`. Если задача
явно требует необязательной проверки регистрации Codex, используй
[условия передачи задачи между потоками](references/cross-thread-task-delegation.md).
