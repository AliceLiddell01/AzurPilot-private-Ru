# Конфликты, слияние и очистка

## Продвинувшаяся база

1. Получи базу через `git fetch`, сохрани её точный SHA и
   `git merge-base <base> HEAD`. Сравни пути обеих сторон от общего предка.
2. Установи намерения изменений обеих сторон по diff, вызовам и тестам.
   Объедини совместимые изменения по смыслу. Конфликт производного файла
   сначала разреши в исходнике, затем запусти канонический генератор или sync.
3. Опубликованную ветку обновляй merge актуальной базы без force и переписывания
   истории. Rebase допустим лишь для неопубликованной истории по политике.
   Whole-file `--ours`/`--theirs` и общая стратегия выбора стороны не заменяют
   смысловое решение. Не удаляй чужие изменения.
4. Проверь отсутствие unmerged paths и активной merge/rebase, происхождение
   новой базы и итоговый diff. Повтори затронутые проверки и генерацию, создай
   коммит и опубликуй по навыку.
5. Изменение HEAD инвалидирует прежние CI и ревью. Получи проверки нового HEAD;
   сначала обнови локальное описание PR, затем опубликуй и перечитай его.
   Новое продвижение базы требует повторной проверки актуальности.

## Merge и очистка

Соблюди порядок GIT-WORKFLOW.md: финальное пользовательское ревью → отдельная
текущая команда на конкретный PR → свежая проверка точного HEAD. Старое
разрешение после существенных изменений недействительно.

Подтверди repository/base/head, статус PR, актуальность базы, обязательные
`Python`/`Windows`/`Security`, ревью и отсутствие блокирующих обсуждений.
После разрешения перевод Draft в Ready выполняется `gh pr ready` с повторным
чтением. Проверь справку установленного инструмента, создай маркер; для обычного
небольшого или среднего PR используй
`gh pr merge <number> --repo <owner/repository> --squash --match-head-commit <sha>`.
Merge commit требует важной самостоятельной истории, rebase merge — обоснования.
Не обходи проверки через `--admin`. Auto-merge требует того же отдельного
разрешения; ожидающее слияние не считается `merged`. Прочитай статус `merged`
и merge SHA перед снятием маркера и очисткой.

После подтверждённого merge получи базу и выполни относящуюся к изменению
проверку. Сохрани чужие изменения и нужные артефакты. Переключи чистую основную
копию на базу и обнови только FF-only. Удаляй ветку через `git branch -d` после
доказанного сохранения результата. Если squash мешает `-d`, оставь ветку и
сообщи ограничение; автоматический переход к `-D` запрещён. Удалённую ветку
удаляй после проверки её принадлежности и слияния. Удаляй только собственные
артефакты. Managed worktree архивируй через инструменты приложения после
проверки других зависимых задач. До merge оставляй ветку задачи и Draft PR.

## Upstream

`master` — чистое зеркало `wess09/AzurPilot:master`. Получи origin/upstream,
подтверди идентичность и ancestry. Ветка `sync/upstream-master-...` начинается
точно от `upstream/master`; Draft PR описывает диапазон и риски, проходит проверки.
После отдельного разрешения допустим только fast-forward push без force и
проверка равенства `origin/master == sync branch == upstream/master`.
Обычный `gh pr merge`, squash и rebase для зеркала запрещены. При divergence
остановись. Перенос в `personal/stable` выполняй отдельным PR с сохранением
отличий форка, миграцией и расширенными проверками.

Обновление пользовательской копии также выполняет штатный Git через этот навык.
Останови среду выполнения, проверь локальную историю и чистоту. После FF-only
отдельно выполни применимые `azur build`/`azur repair`, резервное копирование
PostgreSQL и согласование MCP по их контрактам. Git не выполняет резервное
копирование, синхронизацию зависимостей или приёмку среды автоматически.
