# Git и PR AzurPilot

Этот навык — единственный владелец процедуры Git/PR. Политика веток, запреты,
разрешение слияния и откат принадлежат
[GIT-WORKFLOW.md](../../../.codex/context/GIT-WORKFLOW.md), общая матрица проверок —
[08-VERIFICATION.md](../../../.codex/context/08-VERIFICATION.md).
При разработке автоматически переходи сюда, когда достигаешь этапа Git/PR.
Сам выбор навыка не разрешает слияние или запуск внешнего проверяющего.

## Владельцы инструментов

- Штатный `git` — локальные `status`/`diff`/`log`/`rev-parse`/`merge-base`,
  `branch`/`switch`, `add`/`restore`/`commit`, `fetch`, `merge`/`rebase`,
  разрешение конфликтов, `push` и проверка точной удалённой ссылки.
  Не вызывай для них `azur` или обёртку Python.
- `gh` — канонический путь изменений GitHub для текущей рабочей копии:
  Draft PR, изменение title/body через `--body-file`, Ready/Draft и разрешённый
  merge. Для короткой проверки сразу после изменения допустим `gh ... --json`.
- GitHub MCP — предпочтительное структурированное чтение удалённых данных:
  метаданные PR, файлы, коммиты, diff, reviews/comments/threads,
  Actions/check runs/jobs/logs, compare и проверка других репозиториев.
  Локальное состояние читается через git. Обнаружь реально доступные инструменты
  и их схемы; имена инструментов и возможность записи не предполагаются.
  Не обходи обязательный файл описания через MCP `body` write.
- Если MCP недоступен, разрешает только чтение или не имеет нужного инструмента,
  используй для этого чтения `gh pr view --json`, `gh pr checks`,
  `gh run view --json` либо зафиксируй ограничение.
  Ошибка записи через `gh` не разрешает молчаливый переход к записи через MCP.
  `gh api`/`curl` допустимы лишь при конкретной доказанной отсутствующей
  возможности, с обоснованием; не перебирай способы вызова вслепую.

Перед первым использованием проверь установленный `gh --version` и относящийся
к операции `gh pr create|edit|ready|merge --help`, доступные поля JSON и
возможности MCP. Не закрепляй версии и имена инструментов как вечный контракт.
Неинтерактивные команды выполняй с `tty: false`; не выводи учётные данные или
сырой ANSI/VT/OSC.

## Ветка, индекс и коммит

1. Подтверди идентичность репозитория, status, текущую ветку/upstream, HEAD,
   активную merge/rebase и принадлежность всех изменений. Сохрани пользовательские
   изменения. Проверь fetch URL и push URL, не раскрывая учётные данные.
2. Для upstream sync сразу используй раздел Upstream в
   [references/conflicts-and-merge.md](references/conflicts-and-merge.md): его
   ветка начинается точно от `upstream/master`, а не от персональной базы.
   Для новой обычной задачи получи `git fetch origin`, проверь актуальный
   `origin/personal/stable`, обнови чистую локальную базу только FF-only и создай
   ветку задачи по действующей политике. Продолжение использует существующую ветку
   после проверки HEAD и PR. Не создавай вспомогательные удалённые ссылки.
   Для stacked PR родительская ветка должна быть реально опубликована и её
   удалённый SHA должен совпадать с локальным; иначе остановись и опубликуй
   родителя по этому же навыку.
3. Прочитай итоговый diff, получи base SHA и merge-base. Выполни относящиеся к
   изменению проверки; влияние на MCP обрабатывается по владельцу проверок через
   `azur mcp sync --base <exact-base-sha>`, а не через обёртку Git.
4. Добавь только проверенные пути задачи через `git add -- <paths>` (для удаления
   используй соответствующий путь). Проверь `git diff --cached`, состав индекса
   и отсутствие случайных файлов. Не включай `.codex/local/` и чужой staging.
5. Выполни реальный сканер секретов по содержимому индекса, затем создай логически
   цельный `git commit` с русским Conventional Commit message. Проверь HEAD,
   родителя и итоговый diff коммита; просканируй точный диапазон base..HEAD перед
   push. Gitleaks с redaction проверяет исходники/индекс и диапазон коммитов,
   а не `.venv`. Проверь `gitleaks --help` и флаги установленной версии.
   Например, staged patch можно сохранить локальным файлом и проверить
   `gitleaks stdin --redact` через stdin, диапазон —
   `gitleaks git --redact --log-opts=<base>..<head> <root>`.
   Ручной regex не заменяет сканер; при его недоступности останови публикацию.

## Публикация и неоднозначность

Перед push получи `git ls-remote --refs origin refs/heads/<branch>`; сравни
точный SHA и историю, а не доверяй tracking ref. Отправляй только ветку задачи
явным `git push origin refs/heads/<branch>:refs/heads/<branch>` без force.
При первой публикации настрой upstream этой же ветки через `--set-upstream`;
не оставляй отслеживание базы после публикации.
После команды обязательно прочитай удалённую ссылку ещё раз и сравни с ожидаемым
HEAD. PR create/edit также требует немедленного повторного чтения до завершения
ответа.

Перед публикацией создай и перечитай маркер по
[references/publication.md](references/publication.md). Его присутствие обозначает
только активный/неоднозначный push или изменение PR; это не журнал и не модель PR.
При тайм-ауте, прерывании или неизвестном результате сохрани маркер и описание.
Сначала установи фактическое удалённое состояние только чтением. Не повторяй
push, create или edit вслепую. После доказанного успеха либо доказанного отсутствия
изменения удали только принадлежащий этой операции маркер. Если состояние нельзя
установить, сообщи препятствие и продолжай ограниченное восстановление по справочнику.
При переходе с прежней установки сначала выполни
[references/migration.md](references/migration.md).

## PR: сначала файл, потом GitHub

Создание и существенное редактирование PR выполняются только в этом порядке:

1. Собери факты из фактических base/head, diff, выполненных проверок, состояния
   CI/ревью и ограничений. Проверь отсутствие дублирующего PR для repository/base/head.
2. Создай gitignored repository-local `.codex/local/pr/<task>/body.md`, убедись
   через `git check-ignore`, что файл игнорируется и не tracked. Полностью
   сформируй русское описание по [references/pr-body.md](references/pr-body.md).
3. Перечитай файл целиком и проверь смысл, факты, repository/base/head, секреты
   и завершённость. Сохрани файл минимум до подтверждённого повторного чтения.
4. Создай маркер, затем Draft PR:
   `gh pr create --repo <owner/repository> --base <base> --head <branch> --draft --title <title> --body-file <file>`.
   После создания обязательно прикрепи URL через `attach_artifact`, если доступен.
5. Прочитай опубликованный PR: например,
   `gh pr view <number> --repo <owner/repository> --json url,title,body,isDraft,baseRefName,baseRefOid,headRefName,headRefOid,headRepository,headRepositoryOwner`.
   Сверь полный body с локальным файлом (допустима только нормализация CRLF/LF),
   title, repository/base/head и Draft. Затем сними маркер.

Для edit: обновить локальный `.md` → перечитать и проверить → маркер →
`gh pr edit <number> --repo <owner/repository> --body-file <file>` → повторное чтение
→ снять маркер. При необходимости меняй title тем же прямым subcommand.
Запрещены `gh pr create --body`, `gh pr edit --body`, `--body-file -`, heredoc
непосредственно в вызове провайдера и GitHub MCP `body` write в нормальном локальном
порядке работы. Не удаляй единственный файл описания при неизвестном результате.

## Проверка, конфликты и завершение

Получи свежие PR/CI/reviews через MCP или оговорённый резервный путь чтения.
Сопоставь все проверки с точным HEAD коммита; старый CI не подтверждает новый
коммит. Обработай доказанные замечания, запрошенную внешнюю проверку делегируй
её владельцу. Перед передачей пользователю проверь обязательный CI и блокирующие
обсуждения, обнови описание через файл и повторное чтение.
По политике проекта сохраняй Draft для финального пользовательского ревью;
Ready (`gh pr ready`) и возврат Draft (`--undo`) выполняй только при
соответствующем текущем разрешении/политике с последующим повторным чтением.

Если base продвинулась или появились конфликты, открой
[references/conflicts-and-merge.md](references/conflicts-and-merge.md): объединение
сохраняет смысл обеих сторон, производные файлы пересоздаются из исходников.
Этот справочник также владеет защитой merge по точному HEAD, upstream FF-only
и очисткой. Успешный CI не разрешает merge: требуется отдельная текущая команда
пользователя после финального ревью. До неё конечный результат — проверенный
Draft PR и `READY_FOR_CHATGPT_REVIEW`; при недоступной обязательной проверке — `blocked`.
