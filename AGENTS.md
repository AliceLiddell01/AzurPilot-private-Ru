# Инструкции Codex для AzurPilot Private RU

## 1. Роль

Этот файл — короткий обязательный контракт и карта входа. Он задаёт только
глобальные инварианты и маршрутизацию к владельцам правил, но не дублирует их.

Отвечай пользователю, пиши документацию, операторский текст и сообщения коммитов
на русском языке. Точные имена кода, API, протоколов, пакетов, путей и внешних
инструментов сохраняй как есть.

## 2. Источники истины

Используй источники в таком порядке:

1. код и конфигурация целевой ветки;
2. исполняемые тесты, сгенерированные контракты и подтверждённое поведение;
3. эксплуатационные контракты и вики персонального форка;
4. относящиеся к задаче документы `.codex/context/`;
5. основная версия `wess09/AzurPilot` и её изменения;
6. DeepWiki как карту унаследованного слоя;
7. исторические отчёты.

При расхождении документации с кодом сначала устанавливай фактическое поведение.

## 3. Маршрутизация контекста

Перед инженерной задачей открой `.codex/context/INDEX.md` и загрузи только
документы, относящиеся к фактической области изменения.

Владельцы общих правил:

- Git, ветки, PR, слияние, откат и очистка — `GIT-WORKFLOW.md`;
- общие проверки и критерии готовности — `08-VERIFICATION.md`;
- инструменты Python и внешние интеграции — `11-PYTHON-TOOLING.md`;

Не создавай в этом файле вторую копию правил этих документов.
`MIGRATION-MAP.md` — историческая справка и не входит в обычный рабочий
контекст.

Для нетривиальных инженерных задач проактивно используй субагентов при наличии
независимых направлений; корневой агент сохраняет общие изменения и интеграцию. Подробная
политика принадлежит `.codex/context/12-SUBAGENT-ORCHESTRATION.md`.

## 4. Долговременные инженерные инварианты

- Не зашивай данные конкретной задачи, события, карты, OCR-сценария, PR или
  миграции в продуктовый код, постоянные тесты и CI. Используй существующие
  конфигурацию, реестр, модель, схему, слой абстракции или сгенерированный исходник.
- Постоянные тесты и CI проверяют текущее продуктовое поведение, а не историю
  разработки или разовые снимки свидетельств.
- Если файл попал в набор изменений, проверь весь его человеческий текст. Комментарии,
  операторские сообщения и диагностика должны быть литературным русским, кроме
  точных технических идентификаторов.
- Перед ручным изменением выясни, является файл исходником или сгенерированным
  результатом. Меняй источник и запускай существующий генератор.
- Не создавай параллельную архитектуру или нового владельца, если действующего
  владельца можно безопасно расширить.

## 5. Продуктовая граница

Текущий AzurPilot Private RU поддерживает только Global/EN:

- server: `en`;
- package: `com.YoStarEN.AzurLane`;
- WebUI: `ru-RU`;
- канонические assets: `assets/en`.

Унаследованные ветви CN/JP/TW могут оставаться в upstream-коде как совместимость,
но не являются поддерживаемыми вариантами продукта без отдельной задачи на
изменение этой границы.

Игровое взаимодействие сохраняет цикл:

```text
снимок экрана → распознавание состояния → одно допустимое действие → новый снимок
```

Не заменяй его слепой последовательностью кликов и задержек.

## 6. Инструменты Python и интеграции

Проект использует Python `>=3.14.6,<3.15`, `uv`, `uv.lock` и локальную
`.venv`. Не вводи второй путь зависимостей через `requirements*.txt` или
системный `pip` без отдельной подтверждённой миграции.

Инструменты Python, принадлежащие репозиторию, находятся в `azurpilot/`.
`azurpilot.tooling` владеет типизированными сервисными контрактами,
`azurpilot.integrations` — прямыми адаптерами внешних интеграций. Не возвращай
общий шлюз/прокси в критический путь поверх существующего типизированного
адаптера.

Операции Start/Stop/Update/Repair/Build принадлежат `azurpilot.tooling` и
вызываются для действий оператора, принадлежащих проекту, только буквальной прямой командой
`azur ...`, разрешённой через PATH текущей оболочки. `uv`, исполняемые файлы из `.venv`,
`python -m azurpilot`, обёртки PowerShell/cmd и другие программы запуска не являются
запасным путём для уже доступной команды `azur`; при её отсутствии порядок действий
останавливается без небезопасного перехода или исправляет сам `azur`. `uv` остаётся
допустимым для задач управления зависимостями, начальной настройки, проверки и сборки,
где он владеет операцией.

## 7. Безопасность

Не публикуй секреты, токены, пароли, cookie и учётные данные в URL, содержимое
`.env`, локальные конфигурации, дампы, резервные копии и идентификаторы устройства.

Для любых Git/PR-операций следуй только `GIT-WORKFLOW.md`; этот файл не
определяет отдельные исключения для разрушительных операций Git или слияния.

## 8. Проверки и завершение

Выбор проверок, обязательность приёмки в рабочей среде и критерии готовности принадлежат
`08-VERIFICATION.md`. Не создавай здесь вторую матрицу проверок.

Публикация PR, состояние перед финальным пользовательским ревью, разрешение
слияние и действия после слияния принадлежат `GIT-WORKFLOW.md`.

В итоговом отчёте перечисляй только фактически выполненные проверки и реальные
ограничения. Не выдавай непроверенное состояние за успешное.
