# Инструкции Codex для AzurPilot Private RU

## 1. Назначение

Этот файл — основной обязательный контракт для Codex в репозитории `AliceLiddell01/AzurPilot-private-Ru`.

Отвечай пользователю, пиши документацию и сообщения коммитов на русском языке. Имена переменных, функций, классов, модулей и внешних API сохраняй на английском.

Не считай этот файл заменой чтению кода. Он задаёт правила навигации, проверки и безопасной работы.

## 2. Источники истины

Используй источники в следующем порядке:

1. фактический код и конфигурация целевой ветки;
2. исполняемые тесты, generated contracts и подтверждённое поведение;
3. эксплуатационные контракты и Wiki персонального форка;
4. `.codex/context/` как навигационная карта и перечень проверяемых инвариантов;
5. исходный репозиторий `wess09/AzurPilot` и его изменения;
6. DeepWiki исходного проекта как архитектурная карта;
7. старые отчёты, обсуждения и сгенерированные документы.

При расхождении документации с кодом код является главным источником фактического поведения. Перед изменением устаревающей подсистемы перепроверь соответствующие файлы, точки входа и вызовы.

## 4. Назначение форка и ветки

Форк является персональной русской версией AzurPilot.

- `master` — чистое fast-forward зеркало `wess09/AzurPilot:master`.
- `personal/stable` — стабильная пользовательская версия.
- `codex/*` — новые тематические рабочие ветки Codex.
- `chatgpt/*` — legacy-префикс, допустимый только для продолжения уже существующей однозначной задачи.
- `sync/*` — временные ветки синхронизации `master` с upstream.

Не добавляй персональные изменения непосредственно в `master`. Не используй `personal/stable` как черновик. Для новой работы создавай подходящую ветку `codex/*` от `personal/stable`, если регламент или пользователь явно не задаёт другую базу.

Перед изменением зафиксируй:

- целевую ветку;
- базовый SHA;
- состояние рабочего дерева;
- затронутые подсистемы;
- доступные инструменты проверки.

Полный регламент находится в `.codex/context/GIT-WORKFLOW.md`.

## 5. Технологический контур

Проект использует:

- Python `>=3.14.6,<3.15`;
- `uv` и `uv.lock`;
- локальную `.venv`;
- PyWebIO, Starlette и Uvicorn для WebUI;
- ADB/uiautomator2 и дополнительные backends устройства;
- OpenCV, OCR-модели и шаблонное распознавание;
- PowerShell 7.6.x для персонального контура Start/Update/Repair/Build.

Не создавай и не поддерживай `requirements*.txt`, если это не отдельная подтверждённая миграция. Не заменяй `uv` вызовами системного `pip`.

Базовые команды:

```text
uv sync --frozen
uv run python gui.py
uv run python alas.py
uv run python mcp_server_sse.py
uv run ruff check . --select E9,F63,F7,F82 --ignore F821,F722
uv run -m module.config.config_updater
uv run -m dev_tools.button_extract
```

Перед выполнением команды перепроверь её наличие по актуальному проекту. Не выдумывай тесты или build-команды.

## 6. Ключевые точки входа

- `alas.py` — планировщик и диспетчер задач.
- `gui.py` — жизненный цикл WebUI.

- `module/config/` — загрузка, миграция и генерация конфигурации.
- `module/device/` — соединение, скриншоты, ввод и управление приложением.
- `module/ui/` — граф экранов и переходы.

- `scripts/` — персональный эксплуатационный контур.

## 7. Главный инвариант игрового взаимодействия

Игровые действия строятся как цикл:

```text
снимок экрана → распознавание состояния → одно допустимое действие → новый снимок
```

Запрещено заменять этот поток цепочкой «клик → sleep → следующий клик».

В цикле состояния:

- условия завершения проверяй через распознавание состояния;
- для кликов используй существующие интервалы и защиту от повторов;
- после выполненного действия переходи к новому снимку;
- не скрывай бесконечный цикл искусственным большим числом повторов без анализа состояния;
- учитывай `GameStuckError` и `GameTooManyClickError`;
- сохраняй установленную семантику `handle_*`: обычно `True` означает, что состояние изменено и нужен новый снимок, `False` — действие не выполнено. Перед изменением конкретного обработчика проверь его вызовы.

## 8. Конфигурация и локализация

Структурные источники конфигурации находятся в `module/config/argument/`.

Обычно вручную изменяются:

- `task.yaml`;
- `argument.yaml`;
- `default.yaml`;
- `override.yaml`;
- `gui.yaml`;
- `dashboard.yaml`, если он присутствует и относится к задаче.

Генератор создаёт или обновляет производные файлы, включая:

- `args.json`;
- `menu.json`;
- `config_generated.py`;
- `config/template.json`;
- файлы i18n.

Не создавай новый параметр только ручным изменением производного JSON. После изменения источников запусти генератор и проверь полный diff.

Файлы локализации могут содержать вручную поддерживаемые переводы, но структура ключей должна происходить из поддерживаемого генератором источника. Для русского форка отдельно проверь `ru-RU`, миграцию языка и отсутствие непереведённого китайского пользовательского текста. Допустимы только явно обоснованные исключения: оригинальные названия игровых серверов, событий, каналов распространения, собственные имена и внешние metadata, которые должны сохраняться без перевода.

## 9. Сгенерированные файлы и assets

Перед ручным редактированием выясни, является ли файл источником или результатом генерации.

При изменении assets:

- сохраняй фиксированное разрешение и серверное разделение;
- проверяй определение `Button`/`Template` и путь генератора;
- запускай существующий extractor только если затронут его вход;
- не перегенерируй несвязанные assets.

## 10. PowerShell и эксплуатационные скрипты

Для любого `.ps1`, содержащего Git-команды, обязателен `.codex/context/POWERSHELL-GIT-RULES.md`.

Критические требования:

- PowerShell 7.6.x, запуск через `pwsh`;
- не использовать `;` как разделитель выполняемых команд;
- не переносить команды обратным апострофом внутри скрипта;
- каждый Git-аргумент передавать отдельным элементом массива;
- сразу после каждого Git-вызова сохранять `$LASTEXITCODE`;
- не использовать `Invoke-Expression`;
- не использовать разрушительные Git-команды без прямого разрешения;
- для релевантных `.ps1` фактически запускать PowerShell Parser, PSScriptAnalyzer и требуемый Windows smoke;
- отсутствие обязательного PowerShell gate считать инфраструктурным блокером, а не основанием назвать файл готовым;
- не выдавать статический аудит за фактический запуск.

Контракт персональных команд:

- `Start-AzurPilot.ps1` запускает подготовленную установку и не обновляет её;
- `Update-AzurPilot.ps1` владеет обычным обновлением;
- `Repair-AzurPilot.ps1` диагностирует и транзакционно восстанавливает среду;
- `Build-AzurPilot.ps1` подготавливает уже полученный checkout.

Не смешивай их обязанности.

## 11. Безопасность

До коммита и PR проверяй diff на:

- токены, ключи, пароли, cookies и session data;
- `.env`, локальные config, logs, dumps и backups;
- URL с credentials;
- идентификаторы устройства и персональные данные;
- случайные бинарные или архивные файлы.

Не выводи найденный секрет полностью.

Запрещено без прямого разрешения пользователя:

```text
git reset --hard
git clean -fd
git clean -fdx
git checkout -f
git branch -D
git push --force
git reflog expire
git gc --prune=now
```

## 12. Автономная модель и глубина работы

Основная модель ответственности — **100% Codex**. Codex самостоятельно выполняет технический цикл: разведку, реализацию, проверки, Git, PR, независимое ревью, merge, post-merge verification и cleanup. Пользователь не используется как ручной CI, оператор Git или исполнитель промежуточных команд.

Класс задачи выбирается по риску:

- Fast-track — документация, опечатка, очевидная локальная константа без изменения control flow.
- Стандартный — обычное исправление или небольшая функция в одной известной подсистеме.
- Расширенный — `master`, upstream, `personal/stable`, Start/Update/Repair/Build, зависимости, устройство, OCR, combat, Operation Siren, MCP, безопасность или несколько подсистем.

Если класс неочевиден, выбирай более строгий. Если обязательный gate недоступен, завершай задачу fail-closed со статусом `blocked`, не передавая техническую работу пользователю.

## 13. Проверки

Проверяй от дешёвых к дорогим:

1. статический аудит и итоговый diff;
2. syntax/parser;
3. lint/static analysis;
4. точечные тесты;
5. полный релевантный набор тестов;
6. build/dependency check;
7. контролируемый smoke test;
8. secret scan.

Если проверка упала, установи первопричину, исправь текущую реализацию и повтори связанные проверки. Не создавай новую ветку или новый вариант файла только из-за собственной ошибки.

## 14. Документация

При изменении поведения обновляй связанную документацию тем же изменением.

- Персональные Start/Update/Repair/Build, установка и recovery — Wiki форка.
- Унаследованная архитектура — проверка кода, upstream и DeepWiki.
- `.codex/context/` обновляй только при изменении устойчивой архитектурной границы или рабочего контракта.

Не копируй в контекст номера строк, размеры файлов и точное количество методов: такие данные быстро устаревают.

## 15. Итоговый отчёт

В конце укажи:

- что сделано;
- режим задачи;
- целевую и рабочую ветки, базовый SHA;
- изменённые файлы;
- фактически выполненные проверки;
- результат secret scan;
- ограничения среды;
- один точный локальный шаг пользователя, только если он объективно необходим.

Не утверждай, что команда, тест, Parser, PSScriptAnalyzer, GUI или игровой сценарий были запущены, если фактического запуска не было.
