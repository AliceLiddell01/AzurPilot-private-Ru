# Правила создания PowerShell-скриптов с командами Git

Скрипты должны быть совместимы с PowerShell 7.6.x и запускаться через `pwsh`.

Эти требования являются проектным стандартом. Даже если отдельная конструкция синтаксически допустима в PowerShell, её нельзя использовать, когда она прямо запрещена настоящими правилами.

## 1. Общий режим выполнения

В начале скрипта использовать:

```powershell
Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'
$PSNativeCommandUseErrorActionPreference = $false
```

`$PSNativeCommandUseErrorActionPreference = $false` задаётся явно не потому, что без этой строки любой скрипт обязательно сломается, а чтобы поведение не зависело от значения, унаследованного из вызывающей области, профиля или внешнего окружения.

Git и другие нативные программы сообщают результат через код завершения. Поэтому их ненулевые коды должны обрабатываться вручную через `$LASTEXITCODE`.

Общие требования:

1. Не использовать `;` как разделитель выполняемых команд.
2. Каждая команда, операция присваивания и проверка должна находиться на отдельной физической строке.
3. Не использовать однострочные конструкции, содержащие несколько последовательных операций.
4. Не использовать обратный апостроф как средство переноса команды на следующую строку.
5. Для многострочных вызовов использовать массивы аргументов, splatting, круглые скобки или естественное продолжение выражения.
6. Не использовать алиасы PowerShell в скриптах. Писать полные имена командлетов.
7. Для командлетов PowerShell использовать именованные параметры вместо неочевидных позиционных аргументов.
8. Не использовать `Invoke-Expression`.
9. Не запускать Git через `cmd.exe`, `bash`, вложенный `powershell.exe`, вложенный `pwsh` или `Start-Process`, если для этого нет отдельной технической причины.

## 2. Запрет на последовательность команд через `;`

При создании или изменении `.ps1`-скриптов запрещено объединять команды Git, присваивания и проверки кода возврата через `;`.

Каждая операция должна выполняться отдельно:

1. Выполнить команду Git.
2. Сразу сохранить `$LASTEXITCODE` в отдельную переменную.
3. После этого проверить сохранённый код в отдельном `if`, `switch` или другом управляющем блоке.

### Синтаксически недопустимый шаблон

Следующая конструкция не является рабочей ловушкой, а приводит к ошибке парсинга, потому что список инструкций с `;` нельзя помещать непосредственно в условие `if (...)`:

```powershell
if (& git show-ref --verify --quiet $Ref; $LASTEXITCODE -eq 0) {
    # Этот код не должен генерироваться.
}
```

### Синтаксически допустимый, но запрещённый шаблон

Список инструкций можно спрятать в подвыражение `$()`. Такой код парсится, но смешивает stdout Git и `$LASTEXITCODE`, поэтому результат условия может оказаться неожиданным:

```powershell
if ($(& git rev-parse --is-inside-work-tree; $LASTEXITCODE) -eq 0) {
    # Этот код запрещён, даже если он парсится.
}
```

### Правильный шаблон

```powershell
& git show-ref --verify --quiet $Ref
$gitExitCode = $LASTEXITCODE

if ($gitExitCode -eq 0) {
    # Ссылка существует.
}
```

Также запрещены однострочные цепочки:

```powershell
& git command; $gitExitCode = $LASTEXITCODE; if ($gitExitCode -ne 0) { throw 'Ошибка Git' }
```

Перед выдачей результата необходимо проверить весь скрипт и убедиться, что `;` нигде не используется как разделитель выполняемых команд.

Исключение допустимо только для синтаксически обязательных разделителей внутри заголовка классического `for`. Предпочтительно использовать `foreach`, если это не ухудшает логику.

## 3. Поиск и вызов исполняемого файла Git

Перед основной работой получить исполняемый файл Git один раз:

```powershell
$gitCommand = Get-Command git -CommandType Application -ErrorAction Stop
$gitExecutable = $gitCommand.Path
```

Для вызовов использовать полный путь к приложению:

```powershell
$gitArguments = @(
    '-C'
    $RepositoryPath
    'status'
    '--short'
)

& $gitExecutable @gitArguments
$gitExitCode = $LASTEXITCODE
```

Для объектов `ApplicationInfo`, возвращаемых `Get-Command -CommandType Application`, допустимы `.Path` и `.Source`: оба свойства указывают на путь к исполняемому файлу. В новом коде предпочтительно `.Path` как более прямое имя, но существующее корректное использование `.Source` не является нарушением и не требует отдельной стилевой правки.

Запрещено собирать полную команду Git в одну интерполированную строку:

```powershell
$command = 'git -C "{0}" status' -f $RepositoryPath
Invoke-Expression $command
```

Каждый аргумент Git должен передаваться отдельным элементом массива.

## 4. Обязательная валидация входных значений

Нельзя слепо доверять входным параметрам скрипта.

Перед передачей путей, имён веток, тегов, ссылок, удалённых репозиториев и других строковых значений в Git необходимо проверять, что значение не равно `$null`, не является пустой строкой и не состоит только из пробельных символов.

```powershell
if ([string]::IsNullOrWhiteSpace($RepositoryPath)) {
    throw 'Путь к репозиторию не задан.'
}

if ([string]::IsNullOrWhiteSpace($TaskBranch)) {
    throw 'Имя рабочей ветки не задано.'
}
```

Нельзя подставлять `$null` или пустую строку в аргументы Git.

При наличии нескольких обязательных значений каждое из них проверяется отдельно с конкретным сообщением об ошибке.

## 5. Преобразование и проверка пути репозитория

Перед основной работой скрипт должен:

1. Проверить, что путь не пустой.
2. Проверить существование каталога.
3. Убедиться, что путь относится к файловой системе.
4. Преобразовать существующий путь в строковое абсолютное представление.
5. Убедиться, что каталог является рабочим деревом Git, а не bare-репозиторием.

Для получения строкового пути предпочтительно использовать `Convert-Path -LiteralPath`, который сразу возвращает строку.

```powershell
if ([string]::IsNullOrWhiteSpace($RepositoryPath)) {
    throw 'Путь к репозиторию не задан.'
}

if (-not (Test-Path -LiteralPath $RepositoryPath -PathType Container)) {
    throw ('Каталог репозитория не существует: {0}' -f $RepositoryPath)
}

$repositoryItem = Get-Item -LiteralPath $RepositoryPath -Force -ErrorAction Stop

if ($repositoryItem.PSProvider.Name -ne 'FileSystem') {
    throw ('Путь не относится к файловой системе: {0}' -f $RepositoryPath)
}

$RepositoryPath = Convert-Path -LiteralPath $RepositoryPath
```

Не использовать без необходимости:

```powershell
$RepositoryPath = (Resolve-Path -LiteralPath $RepositoryPath).Path
```

`Resolve-Path` возвращает объект `PathInfo` либо коллекцию объектов, тогда как в данном сценарии нужен обычный строковый путь.

### Проверка именно рабочего дерева

Недостаточно проверить только код возврата `git rev-parse --is-inside-work-tree`: для обычного репозитория команда выводит `true`, а для bare-репозитория может вывести `false` при успешном коде завершения.

Необходимо проверять и код возврата, и stdout:

```powershell
$gitArguments = @(
    '-C'
    $RepositoryPath
    'rev-parse'
    '--is-inside-work-tree'
)

$isWorkTreeOutput = & $gitExecutable @gitArguments 2>&1
$gitExitCode = $LASTEXITCODE
$isWorkTree = [string]($isWorkTreeOutput | Select-Object -Last 1)

if ($gitExitCode -ne 0 -or $isWorkTree.Trim() -ne 'true') {
    throw ('Каталог не является рабочим деревом Git: {0}' -f $RepositoryPath)
}
```

Если скрипту допустим bare-репозиторий, это должно быть явно указано отдельным правилом и обработано отдельной веткой логики.

## 6. Валидация имён веток и ссылок Git

Проверки только на `$null` и пробелы недостаточно. Перед использованием имени ветки необходимо проверить его правилами самого Git.

```powershell
if ([string]::IsNullOrWhiteSpace($TaskBranch)) {
    throw 'Имя рабочей ветки не задано.'
}

$branchValidationOutput = & $gitExecutable check-ref-format --branch $TaskBranch
$gitExitCode = $LASTEXITCODE
$validatedBranchName = [string]($branchValidationOutput | Select-Object -Last 1)

if ($gitExitCode -ne 0 -or $validatedBranchName -cne $TaskBranch) {
    throw ('Недопустимое имя ветки Git: {0}' -f $TaskBranch)
}
```

Сравнение результата с исходной строкой не позволяет принять сокращённое выражение вроде `@{-1}` как буквальное новое имя ветки.

Не добавлять `--` между `--branch` и именем ветки: синтаксис этой формы команды — `git check-ref-format --branch <branchname-shorthand>`.

Для полной ссылки использовать однозначное имя:

```powershell
$branchRef = 'refs/heads/{0}' -f $TaskBranch
```

Перед выполнением команды необходимо понимать, ожидает ли она короткое имя ветки или полное имя ссылки.

## 7. Немедленное сохранение `$LASTEXITCODE`

После каждой команды Git необходимо немедленно сохранить `$LASTEXITCODE`.

Между командой Git и сохранением `$LASTEXITCODE` не должно быть:

- других команд;
- вывода через `Write-Host`, `Write-Verbose`, `Write-Warning` или `Write-Output`;
- присваиваний, не являющихся сохранением `$LASTEXITCODE`;
- логирования;
- вызовов функций;
- проверок;
- конвейеров.

Правильно:

```powershell
& $gitExecutable @gitArguments
$gitExitCode = $LASTEXITCODE

Write-Verbose ('Git завершился с кодом {0}.' -f $gitExitCode)
```

Неправильно:

```powershell
& $gitExecutable @gitArguments
Write-Host 'Команда выполнена.'
$gitExitCode = $LASTEXITCODE
```

Не использовать stdout Git как логическое значение успешности:

```powershell
if (& $gitExecutable @gitArguments) {
    # Неправильно: условие зависит от содержимого stdout, а не от exit code.
}
```

## 8. Допустимые коды возврата

Не считать автоматически любой ненулевой код Git критической ошибкой.

Для каждой команды необходимо заранее определить допустимые коды возврата.

Пример команды, где допустим только код `0`:

```powershell
& $gitExecutable @gitArguments
$gitExitCode = $LASTEXITCODE

if ($gitExitCode -ne 0) {
    throw ('Команда Git завершилась с кодом {0}.' -f $gitExitCode)
}
```

Пример `git diff --quiet`, где код `1` означает наличие различий:

```powershell
$gitArguments = @(
    '-C'
    $RepositoryPath
    'diff'
    '--quiet'
)

& $gitExecutable @gitArguments
$gitExitCode = $LASTEXITCODE

switch ($gitExitCode) {
    0 {
        $hasChanges = $false
    }

    1 {
        $hasChanges = $true
    }

    default {
        throw ('Не удалось проверить изменения. Git завершился с кодом {0}.' -f $gitExitCode)
    }
}
```

Нельзя игнорировать неизвестный код возврата.

## 9. Рабочий каталог

Предпочитать передачу пути через `git -C`:

```powershell
$gitArguments = @(
    '-C'
    $RepositoryPath
    'status'
    '--short'
)
```

Не использовать `Set-Location` только ради выполнения Git-команд.

Когда изменение текущего каталога действительно необходимо, использовать `Push-Location` и гарантированное восстановление в `finally`:

```powershell
Push-Location -LiteralPath $RepositoryPath

try {
    # Работа в каталоге.
}
finally {
    Pop-Location
}
```

Скрипт не должен оставлять текущий каталог изменённым после завершения или ошибки.

## 10. Аргументы, пути и pathspec

1. Каждый аргумент Git должен быть отдельным элементом массива.
2. Не объединять несколько аргументов в одну строку.
3. Для путей в командлетах PowerShell использовать `-LiteralPath`.
4. Перед путями и pathspec в командах Git использовать `--`, когда конкретная команда Git поддерживает этот разделитель.
5. Не добавлять `--` механически в позиции, где синтаксис конкретной команды его не допускает.

Пример:

```powershell
$gitArguments = @(
    '-C'
    $RepositoryPath
    'add'
    '--'
    $FilePath
)
```

Нельзя подставлять непроверенные значения в одну командную строку и затем выполнять её через динамическое вычисление.

## 11. Переменные перед двоеточием в интерполируемых строках

В строках с двойными кавычками запрещено помещать обычную переменную непосредственно перед двоеточием.

Официальная документация PowerShell подтверждает причину: переменную перед `:` нужно отделять `${...}` или не использовать интерполяцию вообще. PowerShell пытается трактовать часть между `$` и `:` как модификатор области видимости или пространство переменной.

Запрещено:

```powershell
throw "Ошибка для ветки $TaskBranch: команда Git завершилась неудачно."
```

Допустимо:

```powershell
throw "Ошибка для ветки ${TaskBranch}: команда Git завершилась неудачно."
```

Предпочтительный вариант без неоднозначной интерполяции:

```powershell
throw ('Ошибка для ветки {0}: команда Git завершилась неудачно.' -f $TaskBranch)
```

Правило распространяется на:

- сообщения ошибок;
- строки логирования;
- пары вида `имя: значение`;
- URL;
- метки;
- пути;
- любые интерполируемые строки, где сразу после имени переменной находится `:`.

Перед выдачей скрипта необходимо проверить строки с двойными кавычками на шаблон `$Variable:`.

Каждое такое место должно быть переписано через `${Variable}`, оператор `-f` или другой способ без неоднозначной интерполяции.

Исключение составляют намеренно используемые модификаторы области видимости и пространства переменных:

```powershell
$global:Variable
$script:Variable
$local:Variable
$private:Variable
$using:Variable
$env:PATH
```

`$using:` применяется для передачи значений из вызывающей области в удалённые команды, фоновые задания и параллельные блоки. Корректные конструкции с модификаторами нельзя механически заменять на `${...}`.

## 12. Обработка stdout и stderr Git

1. Не анализировать визуально отформатированный вывод Git, если существует машинно-читаемый режим.
2. Для автоматизации предпочитать `--porcelain`, `--format` и другие стабильные форматы.
3. Не использовать `Out-String` перед разбором вывода без необходимости.
4. Не подавлять stderr без понимания допустимых кодов возврата и без сохранения достаточной диагностики.
5. Если stderr перенаправляется в stdout через `2>&1`, учитывать, что результат может стать массивом строк.
6. Не использовать `--quiet`, если после команды не проверяется `$LASTEXITCODE`.
7. При захвате stdout сначала выполнить Git, сразу сохранить `$LASTEXITCODE`, а разбор вывода выполнять только после этого.

## 13. Обработка исключений

Не использовать пустые блоки `catch`.

Неправильно:

```powershell
try {
    # Работа.
}
catch {
}
```

Нельзя сочетать `Write-Error` и следующий за ним `throw` при глобальном `$ErrorActionPreference = 'Stop'`:

```powershell
catch {
    Write-Error "Не удалось подготовить Git-ветку: $($_.Exception.Message)"
    throw
}
```

При `$ErrorActionPreference = 'Stop'` вызов `Write-Error` становится завершающей ошибкой. Строка `throw` после него может не выполниться, а наружу уйдёт новое исключение вместо исходного.

Если дополнительный контекст не нужен, использовать голый повторный выброс:

```powershell
catch {
    throw
}
```

Если нужен дополнительный контекст, создать новое исключение и сохранить исходное как `InnerException`:

```powershell
catch {
    $message = 'Не удалось подготовить Git-ветку: {0}' -f $_.Exception.Message

    throw [System.InvalidOperationException]::new(
        $message,
        $_.Exception
    )
}
```

Блок `catch` должен:

1. Добавлять контекст только тогда, когда он действительно полезен.
2. Не скрывать исходную причину ошибки.
3. Сохранять исходное исключение через голый `throw` или `InnerException`.
4. Не продолжать работу после ошибки, если состояние скрипта больше нельзя считать корректным.

Для временных файлов, каталогов и изменения состояния использовать `finally`.

## 14. Опасные Git-команды

Без прямого требования пользователя запрещено добавлять:

```text
git reset --hard
git clean -fd
git clean -fdx
git checkout -f
git branch -D
git push --force
git reflog expire
git gc --prune=now
```

В автономном контуре AzurPilot Private RU запрещены все варианты принудительной отправки, включая `--force-with-lease`: они переписывают опубликованную историю и противоречат `GIT-WORKFLOW.md`. При необходимости восстановления создаётся отдельная контролируемая hotfix- или rollback-ветка; опубликованные refs не переписываются.

## 15. Идемпотентность

Скрипт должен корректно переносить повторный запуск.

Повторный запуск не должен:

- повторно создавать уже существующую ветку;
- повторно применять один и тот же коммит;
- удалять результаты предыдущего запуска;
- завершаться ошибкой только из-за уже выполненного шага.

Перед изменяющей операцией необходимо проверять текущее состояние.

## 16. Логирование

Перед изменяющими Git-командами выводить понятное описание операции.

Не выводить в лог:

- токены;
- пароли;
- приватные ключи;
- URL с учётными данными;
- секретные переменные окружения.

При ошибке по возможности сохранять:

- название операции;
- безопасное представление аргументов;
- код возврата Git;
- путь репозитория;
- имя ветки или ссылки.

При формировании строк логирования соблюдать правило `${Variable}:` и не ставить `:` непосредственно после обычной интерполируемой переменной.

## 17. Фактическая и статическая проверка готового скрипта

Перед выдачей результата необходимо выполнить максимально доступную проверку.

### Когда доступен `pwsh`

Обязательно:

1. Проверить синтаксис через PowerShell Parser.
2. Запустить PSScriptAnalyzer с правилами `Error` и `Warning`.
3. Указать фактически использованную версию PowerShell.
4. Честно сообщить результат выполненных проверок.

Пример проверки парсером без выполнения целевого скрипта:

```powershell
$tokens = $null
$parseErrors = $null

[void][System.Management.Automation.Language.Parser]::ParseFile(
    $ScriptPath,
    [ref]$tokens,
    [ref]$parseErrors
)

if ($parseErrors.Count -gt 0) {
    $messages = $parseErrors |
        ForEach-Object {
            'Строка {0}: {1}' -f $_.Extent.StartLineNumber, $_.Message
        }

    throw ($messages -join [Environment]::NewLine)
}
```

Пример запуска PSScriptAnalyzer:

```powershell
$analyzerParameters = @{
    Path = $ScriptPath
    Severity = @(
        'Error'
        'Warning'
    )
}

$analysisResults = Invoke-ScriptAnalyzer @analyzerParameters

if ($analysisResults) {
    $analysisResults |
        Format-Table -AutoSize

    throw 'PSScriptAnalyzer обнаружил ошибки или предупреждения.'
}
```

### Когда физический запуск невозможен

Нельзя писать, что скрипт:

- запущен;
- проверен PowerShell Parser;
- проверен PSScriptAnalyzer;
- успешно выполнен;
- не содержит синтаксических ошибок по результатам запуска.

Вместо этого необходимо:

1. Провести построчный статический аудит текста.
2. Проверить баланс круглых, квадратных и фигурных скобок.
3. Проверить баланс одинарных и двойных кавычек.
4. Проверить отсутствие `;` как разделителя команд.
5. Проверить отсутствие переносов команд через обратный апостроф.
6. Проверить каждый вызов Git.
7. Убедиться, что после каждого вызова Git сразу сохраняется `$LASTEXITCODE`.
8. Проверить обработку допустимых и неизвестных кодов возврата.
9. Проверить обязательные входные значения через `IsNullOrWhiteSpace`.
10. Проверить интерполируемые строки на шаблон `$Variable:`.
11. Проверить блоки `catch` на сохранение исходного исключения.
12. Явно написать, что проверка была только статической и умозрительной.

Отсутствие доступа к `pwsh` не запрещает провести предварительный статический аудит, но в AzurPilot Private RU оно блокирует commit и merge изменения PowerShell-файла по `GIT-WORKFLOW.md`. Статический аудит нельзя выдавать за фактический запуск.

## 18. Финальное требование к ответу

При изменении существующего скрипта необходимо вернуть полный исправленный файл, а не только отдельный фрагмент.

В конце кратко указать:

- какая ошибка была исправлена;
- какие опасные или неоднозначные конструкции удалены;
- как теперь обрабатываются коды Git;
- выполнялась ли фактическая проверка через `pwsh`;
- выполнялся ли PSScriptAnalyzer;
- какие проверки были только статическими;
- какие проверки невозможно было выполнить.

Нельзя заявлять об успешном запуске скрипта, если он не был реально запущен.
