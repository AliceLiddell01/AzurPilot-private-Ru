# Регламент автономной работы с Git для AzurPilot Private RU

Репозиторий: `AliceLiddell01/AzurPilot-private-Ru`  
Исходный репозиторий: `wess09/AzurPilot`

Этот файл — **единственный владелец** правил Git, веток, PR, upstream,
слияния, отката, очистки и их жизненного цикла. Он описывает текущее правило,
а не историю его изменений.

Распределение ответственности: агент выполняет доступную техническую работу до
готового чернового PR; пользователь проводит финальную проверку, а слияние
разрешается только отдельной явной командой, полученной сейчас.

## 1. Область действия

Документ применяется только к `AliceLiddell01/AzurPilot-private-Ru` и регулирует:

- `master`, `personal/stable`, `codex/*`, прежние `chatgpt/*`, `sync/*`;
- синхронизацию с upstream и перенос его изменений в персональный контур;
- Git, PR, CI, проверки, слияние, откат и очистку;
- изменения Python, PowerShell, документации, безопасности и эксплуатационно
  чувствительных компонентов.

## 2. Главный принцип

Штатный жизненный цикл:

```text
задача
→ безопасная предварительная проверка основной рабочей копии + base SHA
→ релевантный контекст
→ план
→ для новой задачи: fetch origin → personal/stable → FF-only → <domain>/<unique-capability-name>
→ реализация логическими слоями
→ точечные проверки
→ самостоятельная контрпроверка Codex
→ финальные относящиеся к задаче проверки
→ внешняя проверка только по явному запросу или обязательному правилу проекта
→ фиксация изменений / черновой PR
→ обязательный CI для точной верхушки ветки
→ `READY_FOR_CHATGPT_REVIEW`
→ ОСТАНОВКА до финальной проверки пользователя
→ [явная текущая команда на слияние]
→ проверка после слияния
→ очистка
→ короткий доказательный отчёт
```

Codex не просит пользователя запускать команды, тесты, Git, CI, создавать PR или проверять промежуточные файлы, если это технически доступно самому Codex. Слияние не является частью автоматического завершения: оно выполняется только после отдельной актуальной команды пользователя и его финальной проверки.

Политика использования субагентов и независимых внутренних проверок принадлежит
`.codex/context/12-SUBAGENT-ORCHESTRATION.md`; этот документ по-прежнему владеет
жизненным циклом Git и публикацией.

## 3. Контекст и источники

Постепенно загружать только нужный контекст.

Приоритет:

1. фактический код/конфигурация целевой ветки;
2. ближайшие исполняемые тесты и поведение среды выполнения;
3. корневой `AGENTS.md` и релевантные файлы `.codex/context/`;
4. README и вики форка;
5. изменения основной версии, задачи GitHub и PR;
6. DeepWiki как архитектурная карта;
7. официальная документация конкретного API/инструмента.

Правила:

- сначала `.codex/context/INDEX.md`, затем только нужные документы;
- `GIT-WORKFLOW.md` читать по релевантным разделам;
- не перечитывать большие документы после каждого небольшого исправления;
- не проводить общий обзор сайтов и документации без конкретного вопроса;
- не расширять область проблемы без фактических данных из графа вызовов, тестов,
  набора изменений или поведения среды выполнения;
- при расхождении документации и кода сначала установить фактическое поведение.

## 4. Архитектурные границы форка

AzurPilot Private RU наследует upstream, но содержит отдельный персональный эксплуатационный контур.

| Область | Типичные риски |
|---|---|
| WebUI/среда выполнения | процессы, порт, жизненный цикл |
| конфигурация/планировщик | состояние, миграция, повторный запуск |
| устройство/ADB | повторное подключение, тайм-аут, различия платформ |
| снимок экрана/ввод/OCR | координаты, пороги, локализация |
| бой/кампания/Operation Siren | автомат состояний, повторы, условия завершения |
| интеграции/MCP | секреты, конфиденциальность, сетевые ошибки |
| `azurpilot.tooling` | Git, `.venv`, обновление, откат |
| производственные данные | миграция, учётные данные, восстановление, откат |

Оценивать сквозной поток только в пределах фактически затронутых границ.

## 5. Возможности

### Базовые

Проверяются в начале:

- репозиторий/рабочая копия Git и чтение базовой ветки;
- Git;
- среда выполнения/менеджер пакетов, без которых нельзя начать конкретную задачу.

### Для конкретной задачи

Проверяются перед первой относящейся к делу проверкой:

- операции GitHub push/PR, проверок, артефактов и слияния;
- проверка инструментов Python для Windows и системных интеграций;
- сканеры секретов и безопасности;
- браузер/WebUI;
- ADB/эмулятор/игра;
- производственная база данных, сеть и среда выполнения;
- внешняя документация.

Не доказывай в начале работы доступность возможности, которая может не понадобиться.

Повторяющийся дефект среды исправляй в настройке или утверждённом исполнителе
проекта, а не очередным разовым обходным решением в каждой задаче.

## 6. Минимальная предварительная проверка и блокировки

До изменения файлов:

1. определить репозиторий и рабочую копию Git;
2. убедиться, что пользовательские изменения не затрагиваются;
3. получить базовую ветку и base SHA;
4. проверить только инструменты, необходимые для начала текущей работы.

Если обязательная проверка продукта недоступна в момент, когда она действительно нужна:

- не выдавать результат как готовый;
- не обходить защиту;
- сохранить безопасную диагностику и полезные коммиты/PR;
- очистить только принадлежащие текущему прогону временные ресурсы;
- завершить задачу со статусом `blocked`.

Специфичные для провайдера правила повторного запуска и ограничения частоты
внешней проверки принадлежат
соответствующему навыку проверки. CodeRabbit запускается только по явному запросу
пользователя или обязательному правилу проекта; отсутствие запроса фиксируется как
`NOT_RUN`, а не как ограничение сервиса.

Не создавай инфраструктурную задачу автоматически из-за одной временной ошибки;
делай это только при устойчивой проблеме или если этого требует контракт задачи.

Перед любой сменой ветки в основной рабочей копии Codex самостоятельно подтверждает:

- ожидаемый путь репозитория, `git rev-parse --show-toplevel` и `origin`;
- текущую ветку и отслеживаемую ветку upstream;
- `git status`, подготовленные, изменённые и неотслеживаемые файлы;
- локальные коммиты, отсутствующие в upstream, и опережение/отставание/расхождение;
- существование целевой удалённой ветки.

Если обнаружены локальные изменения, неопубликованные коммиты или расхождение,
происхождение состояния устанавливается до смены ветки. Нельзя автоматически
выполнять stash/drop, reset, rebase, merge, force-push или удалять неизвестные файлы.

## 7. Классы задач

### Быстрый режим

Только опечатки, формулировки, комментарии, ссылки и очевидные локальные
изменения без правки потока управления, состояния, безопасности или архитектуры.

Минимум:

1. предварительная проверка/base SHA;
2. целевой файл;
3. минимальный набор изменений;
4. форматирование и синтаксис;
5. относящаяся к задаче проверка;
6. итоговый набор изменений и поиск секретов;
7. фиксация изменений/черновой PR;
8. обязательные проверки и достаточная независимая проверка;
9. `READY_FOR_CHATGPT_REVIEW` → остановка до финальной проверки пользователем и отдельной
   текущей команды пользователя.

Быстрый режим не даёт разрешения на слияние. После финальной проверки пользователем и
отдельной актуальной команды запускается обычный этап слияния, включая повторную
проверку точного head и короткий относящийся к задаче запуск после слияния.

### Стандартный

Обычное исправление или возможность в известной подсистеме:

- относящаяся к задаче архитектурная разведка;
- код и тесты;
- точечные проверки;
- сквозная проверка в разумных границах;
- самостоятельная контрпроверка;
- внешняя проверка только по явному запросу или обязательному правилу проекта.

### Расширенный

Используется для:

- `master`, синхронизация upstream, путь обновления `personal/stable`;
- Start/Update/Repair/Build;
- Python, зависимости и `uv.lock`;
- устройство/ввод/OCR/бой/Operation Siren;
- MCP/безопасность/конфиденциальность;
- миграция/восстановление производственных данных;
- нескольких подсистем или риска потери данных.

Если класс неочевиден, выбери более строгий.

## 8. Модель веток

### `master`

Чистое зеркало `wess09/AzurPilot:master`. Изменения только для форка запрещены.
Обновление выполняется только по разделу 9.

### `personal/stable`

Стабильная пользовательская версия и источник автоматического обновления:

```text
origin/personal/stable
```

Не используется как рабочая ветка. Изменения попадают сюда только через PR и
обязательные проверки.

### Ветки возможностей

Новая возможность использует уникальное имя без номера дорожной карты или этапа.
Для новой обычной задачи по умолчанию используется ветка вида
`<domain>/<unique-capability-name>`, заданная контрактом задачи. Одна задача —
одна рабочая ветка. Ошибка теста или исправление реализации не создаёт новую ветку.

`codex/*` остаётся прежним пространством имён для уже опубликованных веток.
Существующую ветку `codex/*` можно продолжить только после проверки точной
идентичности репозитория, принадлежности задачи и head; новые обычные задачи это
пространство имён не используют.

### `chatgpt/*`

Устаревший формат. Существующую ветку можно закончить, если она однозначно
относится к задаче и точная идентичность подтверждена; новые задачи используют формат
`<domain>/<unique-capability-name>`.

### `sync/*`

Только для синхронизации upstream:

```text
sync/upstream-master-YYYYMMDD-<short-sha>
```

## 9. Синхронизация upstream в `master`

### Предварительная проверка

Перед синхронизацией:

1. получить `origin/master` и `upstream/master`;
2. подтвердить удалённые репозитории;
3. подтвердить родство коммитов и возможность fast-forward;
4. просмотреть переносимый диапазон коммитов и набор изменений;
5. выполнить относящиеся к задаче проверки безопасности и секретов.

При расхождении запрещены reset/rebase/force push/обычное слияние.
Синхронизация блокируется и выполняется установленный порядок разрешения
конфликта или расхождения.

### PR синхронизации

Создай `sync/upstream-master-...` точно на `upstream/master`, открой PR в `master`,
укажи старый и новый SHA, диапазон коммитов, существенные подсистемы, проверки и
риски, затем пройди проверку и CI.

### Применение

После прохождения проверок выполни только fast-forward без force и подтверди:

```text
origin/master == ветка синхронизации == upstream/master
```

Изменений, относящихся только к форку, быть не должно. Не используй слияние,
squash или rebase-коммит для зеркальной синхронизации.

## 10. Перенос изменений upstream в `personal/stable`

Не переноси upstream механически.

Используй отдельную `codex/port-upstream-<тема>` и:

1. изучи изменения upstream;
2. сохрани намеренные отличия форка;
3. адаптируй персональную среду выполнения и контур PowerShell;
4. обнови тесты и документацию;
5. проверь миграцию и откат;
6. пройди расширенный набор проверок в отдельном PR.

## 11. Основная рабочая копия и дополнительная изоляция

Для последовательной разработки основная рабочая копия проекта в Windows является
обычной рабочей копией Codex. Перед началом новой задачи:

```text
fetch origin
→ переключиться на personal/stable
→ выполнить только fast-forward до origin/personal/stable
→ создать ветку по контракту задачи в формате <domain>/<unique-capability-name>
→ работать в основной копии
```

Если в рабочей копии уже открыта однозначно относящаяся к незавершённой задаче
ветка `codex/*` или другая ветка возможностей, продолжай её после проверки точной
идентичности репозитория и head. После публикации ветки возможности оставляй
рабочую копию на ней, пока PR ожидает проверки; автоматически возвращаться на
`personal/stable` не нужно.

Временный клон/рабочее дерево Git допустимы только при реальной необходимости: параллельная
разработка, опасное воспроизведение/эксперимент, несовместимое состояние
зависимостей или среды выполнения, разрушающая проверка восстановления либо явный
запрос пользователя. Это не вариант по умолчанию и не способ переносить обычные изменения.

Для проверки CodeRabbit используется исполняемый файл текущей ОС в той же
утверждённой рабочей копии реализации: Windows использует `coderabbit.exe`, а
POSIX — `coderabbit`. Адаптер обязан подтвердить точные repository/root/base/head,
чистоту индекса и рабочей копии, а также постусловие того же варианта изменений;
отдельный клон или рабочее дерево Git, маршрут UNC, мост WSL и оболочка не являются допустимой заменой.

Для публикации набора связанных PR используй только реально опубликованную
родительскую ветку. Запрещены `codex/base-*`, временные, черновые, транспортные и
вспомогательные ссылки на удалённые ветки, а также вспомогательная публикация.
Если локальный HEAD родительской ветки ещё не совпадает с её удалённым HEAD,
утверждённый порядок публикации и PR возвращает типизированный результат
`TOOLING_STACKED_PARENT_UNPUBLISHED` и не создаёт обходную ссылку.

В любой дополнительной среде base SHA фиксируется до изменений, пользовательские
конфигурации и секреты не копируются без необходимости, временные артефакты
отделяются, а после завершения удаляются только ресурсы текущей задачи. Раздел 22
регулирует разрушающие операции Git во временной среде.

## 12. Рабочий цикл

### Разведка

- актуальное состояние ветки и PR;
- base SHA;
- класс задачи;
- относящиеся к задаче код, тесты, история и контекст;
- затронутые границы;
- риски, проверки и откат.

### План

Зафиксируй результат, границы задачи, ожидаемые изменения, проверки, контрольные
этапы проверки, критерии остановки до `READY_FOR_CHATGPT_REVIEW`, а также
отдельный план проверки после слияния и отката. Не создавай отдельный файл плана
без необходимости.

### Реализация

После заморозки варианта изменений, затрагивающего MCP, выполни одну команду
`azur mcp sync --base <exact-base-sha>`. Результат `NO_CHANGES` или `SYNCED` —
конечный; второй вариант включает завершение подготовки исходников и версии
относительно базы, проверку созданных артефактов, безопасное восстановление
только принадлежащей проекту среды выполнения и приёмку новым клиентом. При
изменении набора исходников повтори синхронизацию: версия будет пересчитана
относительно точной базы и текущего варианта изменений. Неизвестное или чужое
владение, конфликт порта, ошибка остановки/запуска или несоответствие
постусловию требуют безопасной остановки без обхода защиты. Текущее состояние
внешней сессии Codex не является постусловием; горячая перезагрузка не
предполагается. Сгенерированные артефакты MCP входят в общую публикацию задачи.

Для любого действия оператора, принадлежащего проекту и представленного через
`azur`, допустим только буквальный вызов `azur ...` из PATH текущей оболочки.
`uv run`, `python -m azurpilot`, `.venv/.../azur`, абсолютный путь к исполняемому
файлу и оболочка-обёртка — запрещённые обходы, а не равнозначные формы. `uv`
разрешён для задач управления зависимостями, начальной настройки, проверки и
сборки, где он владеет операцией.

- минимальный связный набор изменений;
- не форматировать посторонние файлы;
- менять зависимости и сетевые источники только с обоснованием;
- не создавать `_v2/_final/_fixed` вместо исправления текущего файла;
- обновлять тесты и документацию вместе с поведением.

### Проверка

Порядок:

1. статический анализ/синтаксис/разбор;
2. линтер/статический анализ;
3. точечные тесты;
4. контрпроверка Codex изменений от base до head;
5. внешняя проверка только по явному запросу или обязательному правилу;
6. полный относящийся к задаче набор тестов перед PR/финальной контрольной точкой;
7. проверки зависимостей, сборки, безопасности и секретов;
8. ограниченный проверочный запуск;
9. приёмка через GUI/браузер/эмулятор/игру только для соответствующей области;
10. итоговый набор изменений.

Не повторяй полный набор тестов после каждого небольшого исправления. Сначала
повторяй только затронутые проверки. Полный запуск нужен после существенного
изменения кода, изменения общего контракта/зависимостей или для диагностики.

После PR обязательный CI для точного head является авторитетным повтором
постоянных проверок; не дублируй локально весь CI без причины.

## 13. Последовательные этапы одного Codex

### Этап реализации

Разведка, реализация, тесты, документация и первичная диагностика.

### Самостоятельная контрпроверка

Перечитай фактический набор изменений от base до head как незнакомое изменение и ищи:

- несоответствие задаче или выход за её границы;
- пропущенные места вызова;
- регрессии и обработку ошибок;
- обход или чрезмерную блокировку защиты;
- идемпотентность и параллельность, если они относятся к задаче;
- недостаточные тесты или документацию;
- нарушения правил работы с Git.

Собственные прежние объяснения не считаются доказательством корректности.

### Этап проверки безопасности

Для чувствительных или расширенных изменений тот же основной Codex отдельно
проверяет границы доверия, замечания, подтверждение и оценку серьёзности,
проверку исправлений, секреты и конфиденциальность. Внешний сканер или проверяющий
остаётся независимой проверкой, если он предусмотрен проектом.

## 14. Контракт Start/Update/Repair/Build

```text
azur webui start
azur update
azur repair
azur build
```

- **Start:** запускает подготовленную установку; не владеет Git update.
- **Update:** единственный владелец пути обновления; безопасная схема
  `fetch → проверка истории → merge --ff-only`; без reset/rebase и уничтожения локальных изменений.
- **Repair:** диагностирует и транзакционно восстанавливает `.venv`, сохраняя
  состояние для отката до успешной проверки.
- **Build:** подготавливает уже полученную рабочую копию; не клонирует репозиторий,
  не подменяет Update и не уничтожает конфигурацию; проверяет хеши загружаемых артефактов.

Изменение одной команды не должно захватывать обязанности другой. Приёмка в Windows
проверяет эти типизированные службы Python, а PowerShell остаётся только
вспомогательным средством запуска.

## 15. Python и зависимости

Формальный контракт задаётся `pyproject.toml`/`uv.lock`; текущая проверяемая среда
выполнения Windows — Python 3.14.6.

Не выдумывать команды: сначала читать фактический `pyproject.toml`, `uv.lock` и `docs/ci.md`.

При изменении зависимости обязательны согласованность lock-файла, чистая
синхронизация по lock-файлу, относящиеся к задаче тесты и проверка отката,
проверка исходного кода и уязвимостей, а для новой зависимости — проверка лицензии.

## 16. Секреты

Не записывай и не выводи секреты в репозиторий, журналы и артефакты, а также не
переноси пользовательскую конфигурацию во временную рабочую копию без необходимости.

Сканирование секретов обязательно перед публикацией относящихся к задаче изменений
и перед слиянием, если после предыдущего сканирования они менялись.

Проверяй как минимум изменения исходников, новые архивы и двоичные файлы, `.env*`,
конфигурации/журналы/дампы/резервные копии, ключи/токены/cookie/заголовки
авторизации и персональные идентификаторы.

При обнаружении секрета заблокируй публикацию и слияние, удали его из рабочего
дерева, проверь историю текущей ветки и при утечке в remote используй доступный
порядок отзыва/замены секрета, не публикуя его значение.

## 17. Графический интерфейс, эмулятор и игровая проверка

Запускай такую проверку только когда изменение действительно её требует.

- тестовая конфигурация изолирована;
- необратимые действия в игре, покупки и трата ресурсов запрещены;
- для OCR сохраняются только безопасные артефакты и показатели;
- проверяются тайм-ауты, повторы и условия завершения;
- после теста очищаются принадлежащие задаче процессы, сессии и профили.

Если обязательная безопасная приёмка невозможна, слияние чувствительного изменения блокируется.

## 18. Коммиты

Коммит должен быть логически цельным. Не дроби задачу ради формального числа
коммитов и не создавай новый коммит для каждой правки замечания, если squash/amend
безопасны и политика ветки это допускает.

Перед коммитом:

- итоговый относящийся к задаче набор изменений;
- обязательные проверки форматирования, синтаксиса и затронутой области;
- сканирование секретов;
- отсутствие случайных файлов.

Сообщение описывает смысл изменения (`fix(update): ...`, `feat(build): ...`), а не `fix/final/test`.

## 19. PR, проверка и слияние

PR обязателен для `master`, `personal/stable`, стандартных и расширенных задач,
изменений зависимостей или безопасности, а также Start/Update/Repair/Build.

Текст описания PR должен быть сформирован из типизированной структурированной
модели через временный внешний Markdown-файл и `--body-file`, а затем прочитан
обратно. Обязательны разделы
`Цель`, `Область изменений`, `Реализация`, `Проверки`, `CI`, `Безопасность / проверка секретов`,
`Проверка CodeRabbit и решение по результатам`, `Готовность`, `Миграция / откат`,
`Ограничения`.
В тексте фиксируются точные идентификаторы repository/base/head, base SHA,
подсистемы, фактически выполненные проверки, результат проверки безопасности,
сведения о миграции и откате, ограничения и предполагаемый способ слияния.
Запрещены передача текста описания непосредственно через оболочку командной строки и неявный выбор
репозитория.
Описание PR должно быть полноценным русскоязычным отчётом для человека, а не
кратким автоматическим резюме: каждая секция содержит конкретные факты, а в
области изменений, реализации, проверках, CI, безопасности, откате и ограничениях
используются маркированные пункты. Английский допустим только для точных
технических идентификаторов, названий API и инструментов, маркеров протокола,
названий проверок CI и других специальных слов, которые нельзя безопасно
переводить. Формирователь отклоняет почти пустое описание до вызова провайдера.

Обычная публикация выполняется одной командой `azur delivery publish
--message <commit-message>`; `--path` задаёт необязательную явную область
изменений, иначе инструмент включает все изменённые пути варианта. Он формирует
закрытый манифест в памяти с точными repository, branch/base/head, remote,
preimage/postimage и allowlist. Codex не создаёт JSON-манифест и не вызывает
`validate MANIFEST` перед публикацией. В индекс добавляются только пути из снимка
allowlist; Gitleaks проверяет подготовленные пути и точный диапазон коммитов.
`push` выполняется обычным явным refspec без force/force-with-lease, после чего
проверяется точный SHA удалённой ветки. Неизвестный результат `push` требует
восстановления в режиме только для чтения без слепого повтора.

Проверяй PR в GitHub с явными `--repo`, `--base`, `--head`, режимом `draft` и
повторным чтением точных идентификаторов. В описании PR сохраняется раздел
CodeRabbit для типизированных подтверждений;
если проверка не запрошена, в нём указывается `NOT_RUN` и «не запрошено». Только
явная команда пользователя запускает CodeRabbit; правила запуска и разбора его
результатов описаны в [отдельном навыке](../../.agents/skills/azurpilot-coderabbit-review/SKILL.md).

### Внешняя проверка

Внешняя проверка не является обязательным этапом для каждой задачи. Запускай её
только по явной команде пользователя или обязательному правилу проекта. Для
CodeRabbit незапрошенная проверка остаётся в состоянии `NOT_RUN` и не считается ограничением;
если пользователь запросил проверку, следуй соответствующему навыку, фиксируй результат для точного коммита
и разбирай значимые замечания по его правилам. Результат проверки не
заменяет тесты, CI, проверки безопасности или явное разрешение на слияние.

Если навык CodeRabbit вернул `rate_limited`, жизненный цикл Git может достичь
`READY_FOR_CHATGPT_REVIEW`, когда внешняя проверка не требуется по правилу проекта
и нет значимых замечаний или блокирующих обсуждений. Это не
отменяет обязательные CI, проверку безопасности и секретов, обязательную приёмку продукта
или блокирующие обсуждения. Правила ожидания, повторного запуска и разбора результатов
сервиса описаны в соответствующем навыке и справочнике.

Готовность фиксируется типизированным состоянием: обязательная проверка имеет `PASS`, `FAIL`,
`BLOCKED_PRECONDITION` или `NOT_REQUIRED`; если MCP impact равен `REQUIRED`,
`fresh_mcp_client_acceptance` является обязательной проверкой, не может иметь
`NOT_REQUIRED` и получает `PASS` только при наличии свидетельств от независимого
нового MCP-клиента или сессии, включая initialize, согласованный каталог,
контракт и вызовы только для чтения. Проверка регистрации Codex хранится отдельно
и не является проверкой продукта.
`FAIL`/`BLOCKED_PRECONDITION`
требует `overall_outcome=BLOCKED` и запрещает `READY_FOR_CHATGPT_REVIEW` и
готовность к слиянию, даже если реализация завершена. Ограничение частоты
провайдера является ограничением внешней проверки и не меняет обязательную
проверку продукта или рабочей среды.

### Слияние

Обязательная последовательность одна:

1. пользователь завершил финальное пользовательское ревью текущего head PR;
2. **после этого** пользователь отправил отдельное текущее сообщение, однозначно
   разрешающее слияние именно этого PR;
3. только затем выполняются повторная проверка точного head и разрешённое слияние.

Старое разрешение, разрешение для другого PR и общая фраза вроде «доведи до
конца» недостаточны. Успешные CI, CodeRabbit и самостоятельная проверка не являются
разрешением на слияние и не заменяют ни финальную проверку пользователя, ни
отдельную текущую команду.

До такой команды черновой PR остаётся в `READY_FOR_CHATGPT_REVIEW`. После команды
состояние переходит в `merge-authorized` и выполняется повторная проверка точного
head. Для `personal/stable` по умолчанию используется squash merge для небольших
и средних PR; merge commit допустим, когда важна самостоятельная история
коммитов. Rebase merge требует отдельного обоснования.

Если после финального пользовательского ревью изменился относящийся к задаче
набор изменений, прежнее состояние `merge-authorized` недействительно: повтори
затронутые проверки и получи новое актуальное разрешение по тому же контракту
перед слиянием.

`master` синхронизируется только процедурой раздела 9.

## 20. Процессы GitHub

Предпочитай существующие повторно используемые процессы и исполнители. Создавай
новый процесс только ради устойчивой повторяемой ценности, а не для разового
запуска, компенсации временно отсутствующего инструмента или дублирования
существующей проверки.

Процесс должен иметь ограниченные разрешения, безопасно работать с недоверенным
PR и соблюдать проектную политику фиксации версий actions.

## 21. Опасные Git-операции

В пользовательской рабочей копии, `master`, `personal/stable` и опубликованных ветках запрещены:

```text
git push --force
git push --force-with-lease
git reset --hard
git clean -fd
git clean -fdx
git checkout -f
git branch -D
git reflog expire
git gc --prune=now
```

Не обходи защиту веток, не переписывай опубликованную историю и не уничтожай
пользовательские незакоммиченные данные.

Во временном клоне/рабочем дереве Git разрушающая очистка допустима только после проверки,
что среда создана Codex для текущей задачи, не содержит пользовательских данных и
секретов, а полезный результат уже сохранён. Предпочтительно удалить всю рабочую копию.

## 22. Ошибки и предел повторов

Для ошибки:

1. сохранить достаточный вывод и подтверждающие данные;
2. определить первопричину;
3. отличить дефект продукта от устойчивого дефекта настройки или исполнителя;
4. исправить текущую ветку или начальную настройку;
5. повторить относящиеся к задаче проверки;
6. самостоятельно проверить изменённую область.

Запрошенную внешнюю проверку после исправления повторяй только если нужно перепроверить
её замечание или проверяющий явно требует повтор. Без запроса пользователя или обязательного
правила новые изменения сами по себе не запускают CodeRabbit.

Предел повторов:

- временный сбой инфраструктуры: до 2 быстрых повторов, если не задана явная пауза;
- число повторов внешнего проверяющего определяется его специальным навыком и контрактом;
- нестабильный тест: до 2 повторов с подтверждающими данными;
- одна первопричина в коде: до 3 циклов исправления и точечной проверки;
- находка безопасности: до 2 циклов исправления и подтверждения.

После исчерпания числа повторов обязательной проверки продукта или безопасности
слияние блокируется, полезное состояние сохраняется, временные ресурсы безопасно
очищаются.

Для незапрошенного CodeRabbit состояние `NOT_RUN` не является ограничением и не
блокирует черновой PR или готовность к пользовательской проверке. Правила
повторного запуска и разбора, специфичные для сервиса, применяются только после
явного запроса и описаны в соседнем навыке.

## 23. После слияния и откат

После слияния:

1. получить SHA слитого коммита;
2. проверить обязательные проверки и состояние слияния;
3. выполнить короткий проверочный запуск, относящийся к задаче;
4. проверить Update/Build/Repair только если затронут эксплуатационный контур;
5. убедиться в ожидаемых изменениях и состоянии;
6. безопасно удалить ветку задачи, рабочую копию и артефакты.

При регрессии не выполняй разрушающий откат автоматически. Используй
контролируемый revert или ветку исправления и ускоренный набор относящихся
к задаче проверок.

## 24. Защита веток

### `master`

- принудительная отправка изменений и удаление ветки запрещены;
- коммиты только для форка запрещены;
- обязательные проверки должны пройти;
- допустимо только узкое автоматическое исключение для fast-forward-синхронизации
  после проверки, если оно уже предусмотрено набором правил.

### `personal/stable`

- принудительная отправка изменений и удаление ветки запрещены;
- PR и обязательные проверки нужны всегда;
- обязательные проверки не являются разрешением на слияние;
- финальная проверка пользователем и его отдельная актуальная команда обязательны
  перед слиянием;
- автоматическое слияние допустимо только после такой команды и при соблюдении
  остальных правил проекта.

### Ветки возможностей

Ветки возможностей, включая ветки с явным доменным префиксом, должны:

- не использовать force push после публикации;
- до слияния сохранять черновой PR и ветку для финальной проверки;
- после успешного слияния удалять ветку согласно правилам очистки;
- сохранять полезную незавершённую ветку при блокирующей проблеме.

## 25. Критерии завершения

### До слияния: `READY_FOR_CHATGPT_REVIEW`

Задача готова к передаче на финальную проверку, когда:

- базовые ветка/SHA и область изменений зафиксированы;
- работа выполнена в основной рабочей копии либо в явно обоснованной дополнительной среде;
- набор изменений минимален и не выходит за границы задачи;
- утверждённая команда `azur mcp sync --base <exact-base-sha>` вернула конечный
  статус `NO_CHANGES` или `SYNCED`; при impact в результат `SYNCED` входят
  сгенерированные артефакты и приёмка новым клиентом;
- выполнены относящиеся к задаче локальные проверки;
- тесты обновлены там, где менялось поведение;
- полный набор тестов выполнен на установленном этапе и не повторялся без причины;
- самостоятельная контрпроверка Codex завершена;
- явно запрошенные или обязательные внешние проверки выполнены;
- незапрошенный CodeRabbit остаётся в состоянии `NOT_RUN`, а не считается ограничением;
- проверки безопасности и секретов выполнены в требуемом объёме;
- обязательный CI успешно завершён на точном head;
- блокирующие обсуждения отсутствуют;
- черновой PR содержит актуальную область изменений, base SHA, проверки и ограничения;
- типизированное состояние готовности не противоречит обязательным проверкам и
  общему результату;
- PR ожидает финальной проверки пользователя;
- последовательность разрешения слияния соответствует разделу `### Слияние`.

### Завершение после слияния

После явной команды пользователя дополнительно обязательны:

- повторная проверка точного head, обязательного CI и блокирующих замечаний;
- слияние разрешённым способом;
- проверка после слияния успешно завершена;
- документация и сведения об откате обновлены, где необходимо;
- принадлежащие задаче временные ресурсы очищены;
- основная рабочая копия и ветки приведены к согласованному состоянию.

Возможность для конкретной задачи не входит в критерии завершения, если
соответствующая проверка не относится к фактической области изменений.

## 26. Обновления хода работы и итоговый отчёт

Во время работы сообщай о ходе только при:

- начале новой крупной фазы;
- факте, который меняет план;
- существенной контрольной точке;
- блокирующей проблеме.

Обновление — 1–2 предложения с конкретным результатом. Не описывай обычные
действия вроде «читаю файл», «запускаю тест», «проверяю Git».

Итоговый отчёт должен быть кратким и подтверждённым фактами. До слияния
используй `READY_FOR_CHATGPT_REVIEW`, после него — `merged`, а при фактически
недоступной обязательной проверке — `blocked`:

```text
Статус: READY_FOR_CHATGPT_REVIEW / merged / blocked / reverted
Git: base SHA, ветка, PR, SHA слияния
Изменено: ключевые файлы/подсистемы
Проверено: фактически выполненные проверки и CI на точном head
Проверка: самостоятельная, внешние этапы, блокирующие замечания
После слияния: относящийся к задаче запуск/проверка или `не применимо до слияния`
Ограничения: только реальные
От пользователя требуется: ничего / неизбежный внешний шаг
```

Не дублируй в итоговом отчёте полные изменённые файлы, длинные журналы тестов и
историю каждого вызова инструмента, если пользователь прямо этого не просил.

## 27. Актуальное состояние

Активные ветки, PR, SHA, состояние CI и upstream не фиксируются здесь как
постоянные факты. Получай их заново перед соответствующей операцией.

## 28. Итоговая политика

Штатный результат до слияния:

```text
проверенный коммит/черновой PR
+ обязательные проверки и CI
+ передача на финальную проверку пользователю
+ остановка до слияния
+ короткий отчёт
```

После отдельной актуальной команды пользователя к этому результату добавляются
разрешённое слияние, проверка после слияния и очистка. Если обязательная
проверка продукта недоступна или не пройдена, корректный результат — сохранённое
полезное состояние и статус `blocked`, а не непроверенное слияние. Ограничение
частоты отмечается как ограничение проверки только тогда, когда пользователь
явно запросил CodeRabbit.
