# Политика Git и PR AzurPilot Private RU

Этот документ владеет долговременной политикой, а процедура принадлежит
[azurpilot-git-workflow](../../.agents/skills/azurpilot-git-workflow/SKILL.md).
При работе с ветками, коммитами, публикацией, PR, конфликтами, слиянием и
очисткой автоматически применяй этот навык.
Публичный `azur` не изменяет Git и не публикует PR; Python tooling читает только
свидетельства Git для самостоятельных возможностей. Не создавай обёртки транспорта.

## Репозиторий и ветки

- Персональный репозиторий: `AliceLiddell01/AzurPilot-private-Ru`.
- Обычная база — актуальный `origin/personal/stable`; локальная база не является
  рабочей веткой. Изменения попадают в неё только через PR и обязательные CI.
- Одна задача — одна уникальная тематическая ветка. Формат
  `<domain>/<unique-capability-name>` выбирается по контракту задачи;
  при действующем требовании Codex использовать `codex/*` соблюдай его.
  Существующие ветки продолжай только после подтверждения принадлежности и HEAD.
- `chatgpt/*` — прежний формат; новые задачи его не используют.
- `sync/*` — только upstream. `master` остаётся чистым зеркалом
  `wess09/AzurPilot:master`; разрешён только проверенный fast-forward без
  коммитов персонального форка, squash/rebase/обычного merge. Процедура находится в навыке.
- Upstream переносится в персональный контур отдельным PR с адаптацией и
  сохранением намеренных отличий форка.
- Stacked PR использует реально опубликованного родителя с подтверждённым SHA.
  Вспомогательные удалённые ссылки и временные транспортные ветки и `codex/base-*` запрещены.

## Рабочая копия и сохранность

По умолчанию используй основную рабочую копию для последовательной разработки.
До изменения состояния проверь состояние, HEAD, upstream, идентичность репозитория, актуальную базу
и активные операции Git. Не уничтожай пользовательские изменения или индекс.
До merge оставляй копию на ветке задачи и сохраняй полезный Draft PR.

Дополнительная изоляция оправдана конкретной необходимостью: параллельная
разработка, опасное воспроизведение/эксперимент, несовместимое состояние
зависимостей или среды выполнения, разрушающая проверка восстановления либо
явный запрос пользователя. Управляемые рабочие копии создаются и архивируются средствами
приложения с проверкой владения; полезное незавершённое состояние сохраняется.

Запрещены force push/force-with-lease, `reset --hard`, `clean -fd/-fdx`,
`checkout -f`, `branch -D`, преждевременное удаление reflog/objects и переписывание
опубликованной истории. Не обходи защиту веток. Во временной принадлежащей
задаче среде очистка допускается только после доказанного сохранения результата
и отсутствия пользовательских данных; удаляй лишь принадлежащие задаче ресурсы.

## Публикация и проверки

Коммиты логически цельные, сообщения — русские Conventional Commits:
`type(scope): краткое описание`. Итоговый набор изменений и подготовленная в индексе область изменений проверяются до
коммита; секреты проверяет реальный сканер по исходникам, индексу и точному диапазону коммитов.
Секреты, учётные данные, локальные конфигурации, дампы и идентификаторы устройства
не публикуются. Ручной regex не заменяет сканер секретов.

Заголовок и описание PR — на русском, кроме точных технических идентификаторов. Локальный
игнорируемый Git файл Markdown, предварительное перечитывание, `gh --body-file`
и полное повторное чтение обязательны; подробная процедура и формат принадлежат навыку.
Не создавай типизированную схему или формирователь PR либо постоянный журнал публикации.

Общая матрица, режимы, число повторов, MCP и приёмка среды выполнения принадлежат
`08-VERIFICATION.md`. При влиянии задачи на MCP требуется конечный
`azur mcp sync --base <exact-base-sha>` (`NO_CHANGES` или `SYNCED`), включая
необходимую приёмку новым клиентом. Оркестрация независимой проверки принадлежит
`.codex/context/12-SUBAGENT-ORCHESTRATION.md`.
Обязательные `Python`, `Windows`, `Security` и ревью относятся к точному HEAD;
изменение HEAD делает недействительными затронутые проверки. Недоступная обязательная проверка
означает `blocked`, а не готовность. Неизвестная публикация требует восстановления
удалённого состояния только чтением до повторного изменения; маркер не удаляется
без подтверждённого постусловия.

CodeRabbit запускается только по явному запросу или обязательному правилу через
`azurpilot-coderabbit-review`; публикацию в Git он делегирует навыку Git.
Незапрошенный проверяющий — `NOT_RUN`, не препятствие. Если навык CodeRabbit вернул
`rate_limited`, жизненный цикл Git может достичь `READY_FOR_CHATGPT_REVIEW`,
когда проверяющий не обязателен и нет доказанных препятствий. Это не отменяет
обязательные CI, проверку безопасности и секретов, обязательную приёмку продукта
или блокирующие обсуждения. Повторы CodeRabbit принадлежат его навыку и справочнику.
После исчерпания числа повторов обязательной проверки продукта или безопасности
слияние блокируется, полезное состояние сохраняется.

### Быстрый режим

Объём проверки определяется `08-VERIFICATION.md`; итог остаётся
`READY_FOR_CHATGPT_REVIEW` и остановка до финальной проверки пользователя.
Быстрый режим не даёт разрешения на слияние.

### Стандартный и расширенный режимы

Применяй матрицу владельца проверок к фактическим изменениям. Не выдавай узкие
тесты за приёмку среды выполнения или старый CI за проверку нового HEAD.

## Финальное ревью и разрешение

До слияния результат — проверенный Draft PR, обязательный CI и
`READY_FOR_CHATGPT_REVIEW`. Пользователь выполняет финальную проверку.
Draft остаётся Draft до соответствующей текущей команды/разрешения; навык
владеет механикой Ready/Draft и повторного чтения.

### Слияние

1. Пользователь завершает финальное пользовательское ревью текущего HEAD PR.
2. После него требуется отдельная текущая команда пользователя, однозначно
   разрешающая слияние именно этого PR.
3. Только затем выполняются повторная проверка точного HEAD и проверок и слияние.

До отдельной команды сохраняется `READY_FOR_CHATGPT_REVIEW`.
Старое разрешение и разрешение для другого PR недостаточны. CI, CodeRabbit и
самостоятельная проверка не являются разрешением на слияние. Общая просьба
«доведи до конца» не заменяет эту последовательность.
После команды состояние `merge-authorized`; изменение существенной области изменений или HEAD
после пользовательского ревью требует новой проверки и актуального разрешения.
Для `personal/stable` обычный небольшой/средний PR сливается squash; merge коммит
допускается для важной самостоятельной истории, rebase merge — с обоснованием.
Auto-merge допустим только при том же отдельном разрешении. Для `master` действует
исключительно политика синхронизации upstream через fast-forward.

## После слияния и откат

После подтверждённого `merged` обязательны merge SHA, актуальная база,
относящаяся к задаче проверка после слияния и безопасная очистка принадлежащих задаче
ветки, артефактов и временной среды. Конкретные действия принадлежат навыку.
При регрессии используй контролируемый revert или исправляющий PR; не выполняй
разрушающий откат автоматически. Обновление рабочей копии не является операцией Python; build/repair/MCP/backup выполняются отдельно по своим контрактам.

## Отчёт

Сообщай кратко: `READY_FOR_CHATGPT_REVIEW`, `merged` или `blocked`; base/head,
ветка/PR, существенные изменения, фактически выполненные проверки и ограничения.
Исторические SHA, PR и запуски CI не становятся постоянными правилами.
