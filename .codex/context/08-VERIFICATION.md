# Проверки и критерии готовности

Этот файл — единственный владелец общей матрицы проверок и критериев готовности.
Проверки выбираются по фактическому diff и изменённой архитектурной границе;
соседние документы и навыки только направляют сюда, а не создают вторую матрицу.

## Нулевая проверка

До изменения файлов выполнить только короткую предварительную проверку:

- подтвердить репозиторий, целевую ветку и base SHA;
- подтвердить, что рабочая среда соответствует заявленному checkout, а пользовательские изменения не будут затронуты; для штатной последовательной разработки используется основной checkout;
- проверить инструменты, без которых нельзя начать именно эту задачу.

Остальные возможности проверяются **по мере необходимости, непосредственно перед первой проверкой, которой они нужны**:

- GitHub: отправка изменений, работа с PR, проверки и слияние — перед соответствующей операцией в GitHub;
- проверки среды выполнения Windows — только если затронут соответствующий адаптер Python
  или интеграция с Windows;
- сканер секретов и безопасности — перед соответствующей контрольной точкой проверок;
- браузер/графический интерфейс/эмулятор/игра — только если изменение действительно требует такой приёмки;
- возможности рабочей среды и сети — только перед проверкой производственной среды или сети.

Не тратить начало задачи на доказательство доступности будущих инструментов, которые могут вообще не понадобиться. Если обязательная проверка оказалась недоступна в момент, когда она действительно нужна, результат получает статус `blocked`: Codex не выдаёт непроверенный артефакт как готовый и не перекладывает рутинный запуск на пользователя.

Постоянную проблему среды нужно устранять на этапе начальной настройки или в каноническом исполнителе проекта, а не диагностировать заново для каждой задачи по разработке функциональности. Не устанавливать и не перенастраивать глобальные инструменты «на всякий случай».

## Постоянный CI

Единственный постоянный рабочий процесс для pull request — `.github/workflows/ci.yml`. Он
запускается для каждого pull request независимо от целевой или базовой ветки и без
`paths`-фильтров. Для защищённой `personal/stable` ruleset делает required три
устойчивых context:

- `Python`;
- `Windows`;
- `Security`.

Исторические номера этапов, зафиксированные свидетельства, привязанные к этапам базовые показатели и временные проверки миграции не являются постоянными проверками качества. Подробный фактический контракт, локальные эквиваленты и правила изменения CI находятся в `docs/ci.md`.

Локально использовать именно команды и исполнитель, определённые в `docs/ci.md`; не воспроизводить среду CI вручную, если проект уже предоставляет канонический способ запуска.

## Режимы

### Быстрый режим

Для документации, опечатки и очевидного локального изменения без изменения потока управления.

Минимум:

- проверить целевой файл и контекст;
- минимальный diff;
- форматирование/синтаксис;
- итоговый diff;
- сканирование секретов перед публикацией изменения.

### Стандартный

Для обычного исправления или возможности в одной известной подсистеме.

Дополнительно:

- проследить релевантные вызовы;
- проверить аналогичную реализацию;
- запустить точечные тесты;
- проверить сквозное поведение в разумной границе;
- выполнить самостоятельную проверку итогового diff;
- внешнюю проверку запускать только по явному запросу или обязательному правилу проекта.

### Расширенный

Для:

- upstream/master/personal stable;
- Start/Update/Repair/Build;
- Python/dependencies/uv.lock;
- устройство/ввод/OCR/бой/Operation Siren;
- MCP/безопасность/конфиденциальность;
- рабочая среда/миграция данных;
- нескольких подсистем.

Требует архитектурного анализа, подходящего набора проверок, самостоятельной проверки изменений и явного описания рисков. Внешние проверки нужны только по явному запросу или обязательному правилу проекта.

## Независимая волна проверки

Существенный вариант изменений или правка, затрагивающая несколько подсистем,
перед финальной готовностью проходит независимую проверку субагентами, если эта
возможность доступна и подходит изменению. Выбирай роли по фактическому diff
согласно `.codex/context/12-SUBAGENT-ORCHESTRATION.md`. Для PR с изменённым
человекочитаемым текстом включай `localization_reviewer` и проверяй весь такой
текст в изменённых PR-файлах.

Независимая волна проверки дополняет, но не заменяет автоматические тесты и CI.
После существенного изменения варианта проверяй повторно только те выводы
проверяющих, область которых затронута этим изменением.

## Внешняя проверка

Codex самостоятельно проверяет каждое изменение. Внешнего проверяющего, включая
CodeRabbit, запускай только по явной команде пользователя или обязательному
правилу проекта. Незапрошенный CodeRabbit остаётся в состоянии `NOT_RUN` и не требует попытки
или отметки об ограничении. Если проверка запрошена, соответствующий навык описывает запуск,
подтверждение точного коммита и разбор результатов; значимые замечания нужно устранить до готовности.

После заморозки варианта изменений, затрагивающего MCP, выполни одну команду
`azur mcp sync --base <exact-base-sha>`. Она сама классифицирует зафиксированные
изменения и состояние рабочей копии; `NO_CHANGES` — конечный результат без
изменений, а `SYNCED` подтверждает комплект сгенерированных файлов, безопасное
восстановление принадлежащей проекту среды выполнения и приёмку новым клиентом.
Не собирай обязательную проверку из отдельных `impact`, `reconcile`, `status` и
`accept`. Изменение набора исходников MCP делает предыдущую синхронизацию
неактуальной; повторная команда пересчитает SemVer относительно точной базы и
текущего варианта изменений. Чужое или неизвестное владение, конфликт порта,
ошибка остановки/запуска или нарушенное постусловие требуют безопасной остановки
без обхода защиты. Текущее состояние внешней сессии Codex не подтверждает
постусловие; автоматическая перезагрузка конфигурации не предполагается.

Проверка регистрации Codex — отдельная необязательная интеграционная проверка.
Если изменение затрагивает регистрацию Codex или плагина, видимую клиенту схему
инструмента или маршрутизацию, её можно выполнить по
[единому контракту продолжения задачи между потоками](../../.agents/skills/azurpilot-repository-development/references/cross-thread-task-delegation.md).
Неверный HEAD, недоступный `create_thread` или другой сбой платформы фиксируется
как ограничение интеграции Codex и не переводит успешно пройденную проверку MCP
клиента в `FAIL` или `BLOCKED_PRECONDITION`.

## Этапы до и после слияния

Критерии готовности до слияния выполнены после фиксации и отправки чернового PR,
проверки обязательных контекстов `Python`, `Windows`, `Security` на точной верхушке
ветки, сканирования секретов, самостоятельной проверки и обработки явно запрошенных
или обязательных замечаний. Итоговый статус —
`READY_FOR_CHATGPT_REVIEW`: финальную проверку выполняет пользователь, а слияние не
выполняется без отдельной текущей команды пользователя.

Типизированная оценка готовности отдельно учитывает реализацию, обязательные проверки,
запрошенную внешнюю проверку, `READY_FOR_CHATGPT_REVIEW` и готовность к слиянию. `NOT_RUN` без явного запроса —
нормальное состояние, а не ограничение. Обязательная проверка имеет
конечное состояние `PASS`, `FAIL`, `BLOCKED_PRECONDITION` или `NOT_REQUIRED`; при
`MCP impact=REQUIRED` `fresh_mcp_client_acceptance` обязателен и `NOT_REQUIRED`
для него недопустим; `PASS` требует свидетельство независимой свежей сессии клиента
MCP; `FAIL`/`BLOCKED_PRECONDITION` сохраняет полезный черновой PR, но задаёт общий итог `BLOCKED`
и не допускает готовность к слиянию. Результат запрошенного CodeRabbit
фиксируется отдельно и сам по себе не заменяет обязательные продуктовые проверки. Проверка регистрации Codex
хранится отдельно и сама по себе не блокирует готовность продукта.

Проверка после слияния и очистка являются отдельным этапом и выполняются только
после подтверждённого слияния. Перед ним нужно повторно проверить точную верхушку
ветки, обязательные проверки CI, относящийся к задаче diff и блокирующие замечания.
Успешный CI или CodeRabbit сами по себе не являются разрешением на слияние.

## Итерации и заморозка варианта изменений

При ошибке сначала повторяй конкретный упавший тест или узел; после исправления
запускай только затронутую короткую проверку. Набор тестов подсистемы запускай один
раз после стабилизации области, а полный относящийся к задаче набор — один раз для
замороженного варианта изменений. Существенный diff кода или конфигурации после него
требует повторной проверки; изменение только описания PR или отчёта этого не требует.
При изменении текста команды, диагностики или документа сначала обнови связанные
буквальные проверки контракта. Для lint используй каноническую проверку, определённую
в репозитории, а не отдельный вызов `ruff check .`.
Исследование можно остановить после определения владельца поведения, цепочки вызовов,
ближайшего контракта и тестов, а также первопричины. Пока выполняется CI, заверши
независимую проверку diff и отчёта; не опрашивай CI часто, а при сбое сразу исследуй
конкретное задание CI.

## Типовая матрица

### Python

- `uv lock --check` и синхронизация по lock-файлу способом, определённым репозиторием, для постоянного CI;
- компиляция/импорт затронутого модуля;
- существующий ruff-профиль;
- точечные тесты во время реализации;
- полный связанный набор один раз перед PR/финальной контрольной точкой, если после него не было существенного diff кода;
- проверка генератора;
- чистое рабочее дерево после генераторов.

Не повторять полный набор тестов после каждого небольшого исправления, если точечные проверки покрывают изменённую область. После PR не дублировать локально тот же полный CI без причины: доверять обязательным проверкам на точной верхушке ветки, а локальный повтор делать при диагностике сбоя или существенном изменении после CI.

### Данные о ресурсах игры

- панель `game_get_resources` явно помечена как проекция по снимкам и истории
  и сохраняет `Dashboard.<resource>.Record` в `last_update`;
- неизвестная или устаревшая временная метка не считается текущим состоянием;
- обязательная проверка в реальной среде использует свежее наблюдение текущего
  состояния, а не снимок панели;
- отображаемые `limit`/`MAX` для Oil не считаются жёстким пределом хранения: `25000` при
  `17050` является допустимым структурным состоянием.

- генератор;
- отсутствие неожиданных изменений сгенерированных файлов;
- загрузка старой конфигурации;
- идемпотентность миграции;
- ru-RU keys/placeholders;
- текущая среда выполнения Global/EN; унаследованные варианты других регионов проверяются только при явной задаче совместимости.

### Распознавание

- положительные снимки экрана;
- отрицательные снимки экрана;
- пороги;
- переходные кадры;
- варианты темы; тестовые данные других регионов — только при явной задаче совместимости;
- проверка допустимого диапазона результатов OCR.

Для сканера Formation/Fleet, управляемого через UI, дополнительно проверять:

- одиночный переходный кадр с положительным результатом детектора не запускает физический сканер;
- открытие Info требует ограниченной последовательности свежих подтверждений состояния;
- закрытие Info требует устойчивой границы Formation до выбора следующего флота;
- исключение на уровне сканера сохраняет физическую диагностику слоя и типа;
- структурный результат `complete == False` остаётся отдельным результатом распознавания и не превращается в физический сбой;
- recoverable continuation разрешён только после доказанного восстановления детерминированного UI состояния;
- при неизвестном состоянии UI пакетная обработка останавливается без автоматического продолжения;
- `failed_fleet_index` и итоговые `PARTIAL`/`FAILED` не допускают false success после физического сбоя.

Если изменение производственного кода затрагивает сам переход между флотами, после автоматических проверок нужна одна контролируемая проверка на реальном устройстве для полного диапазона Surface Fleet 1..6. Не повторять несколько эквивалентных ручных прогонов без новых свидетельств или существенного diff кода.

Проверки на реальном устройстве/OCR и сравнительные испытания выполняются локальными инструментами из `tools/acceptance/` и `tools/benchmarks/`. Они не становятся обязательными проверками каждого PR без отдельного устойчивого обоснования.

### Сохранение русскоязычного текста в среде выполнения

Общий набор pytest запускает `tests/contracts/localization/test_runtime_russianization_audit.py`. Тест выполняет постоянный семантический аудит текущих производственных участков, отображающих текст, и идентичности Global/EN; самопроверки должны подтверждать обе стороны контракта:

- FAIL: операторский текст на CJK-языках, обычное непереведённое английское предложение, псевдоним locale/server/package/assets/OCR другого региона;
- PASS: русский контекст, идентификаторы ADB/OCR/API/URL/path/package/game, отложенный текст исключения и структура функциональности вне места отображения.

Для PR с явной задачей перевода эта проверка дополняет, но не заменяет динамическую структурную проверку от base до head. Для изменений функциональности, исправлений и рефакторинга структурное сравнение не применяется; постоянная проверка русскоязычного текста остаётся обязательной частью обычных тестов продукта.

## Проверка секретов

Перед фиксацией/PR и перед слиянием, если после последнего сканирования менялся относящийся к задаче diff:

- изменения в индексе и итоговый diff;
- новые архивы и двоичные файлы;
- `.env`, config, logs, dumps, backups;
- API tokens, webhooks, credentials, cookies;
- device/user identifiers.

Обязателен фактически запущенный сканер секретов. Ручной поиск по шаблонам может быть только дополнительной проверкой и не заменяет сканер. Если сканер недоступен в момент обязательной проверки, задача блокируется.

Постоянное задание CI `Security` проверяет текущие исходники и относящийся к делу диапазон коммитов PR. Диагностика должна скрывать секреты и загружаться только при сбое.

## Доставка Git и публикация PR

Штатная публикация выполняется одним вызовом `azur delivery publish --message ...` с
необязательными `--path`, задающими явную область изменений. Инструмент сам строит
закрытый типизированный манифест в памяти по точной идентичности репозитория,
базовой ветки, верхушки ветки и remote, а также по снимку выбранных путей. Внешний JSON-манифест и предварительный `validate MANIFEST`
не нужны. Только для чтения `validate MANIFEST` остаётся диагностикой. Команда
публикации добавляет лишь пути из зафиксированного списка разрешённых путей,
подтверждает состав индекса, запускает Gitleaks для выбранного набора по индексу и
точному диапазону коммитов, создаёт коммит с заданным сообщением, выполняет обычную
отправку по явному refspec без force/force-with-lease и затем проверяет точный SHA
удалённой ветки. Тайм-аут или неизвестный результат отправки фиксируется в журнале
и обрабатывается только для чтения командой `recover`; слепой повтор запрещён. По
умолчанию один логически цельный коммит включает все изменённые пути варианта,
в том числе актуальные сгенерированные артефакты MCP.

До подготовки индекса сервис сохраняет исходные SHA/размер результата изменений и
его представление Git blob после нормализации, а после подготовки повторно
сравнивает обе формы с манифестом и индексом. Изменение целевого файла в этом окне
останавливает публикацию безопасным образом. Для удаления наличие в индексе
проверяется отдельным ограниченным запросом: только доказанное отсутствие считается
успехом, ошибка/тайм-аут/усечение ответа считается неизвестным состоянием. Удалённый
репозиторий публикации и `base_remote_name` проходят каноническую проверку идентичности
репозитория; совпавший SHA неправильного remote не принимается.

Человекочитаемая команда `delivery validate` показывает ограниченный отчёт Rich
`Delivery Package` и список изменений `A`/`M`/`D`, заканчивая строкой
`Изменения не применены.`. Вариант с `--json` остаётся одним строгим конвертом с
полными SHA, количеством целевых файлов, сведениями об изменениях и типизированными
свидетельствами без ANSI и человекочитаемой диагностики.

Для чернового PR обязательны явные идентификаторы репозитория, базовой ветки и
верхушки ветки, точные локальный и
удалённый SHA, типизированное структурированное описание и публикация через
временный внешний файл с `--body-file`. После вызова провайдера повторно читаются
идентичность PR и полный хэш описания. После неоднозначного результата,
тайм-аута или неизвестного состояния изменения через `edit` результат повторно
читается до дальнейшей классификации; слепой повтор запрещён. Несовпадение
провайдера, PR из другого репозитория, дублирующий вариант или неподтверждённое
создание являются блокирующей ошибкой.
Описание должно быть подробным русскоязычным отчётом: цель, область и границы,
подсистемы/файлы, фактическая реализация, локальные/приёмочные проверки, CI на
точной верхушке ветки, проверка безопасности и секретов, решение по CodeRabbit,
миграция/откат и ограничения. Формирователь не принимает короткие общие абзацы без
фактов и маркированных списков.

Только если diff затрагивает `azur delivery`, `azur pr`, общий контракт CLI/
инструментов или семантику публикации, приёмка включает человекочитаемый вызов и
вызов для агента с `--json`. JSON обязан содержать ровно один закрытый
результирующий конверт. Для несвязанного исправления боя/OCR/документации эта
проверка CLI не применяется. Она не заменяет проверки CI `Python`, `Windows`,
`Security` на точной верхушке ветки PR.

## Критерии готовности

### До слияния: `READY_FOR_CHATGPT_REVIEW`

- правильная ветка и base SHA;
- минимальный связный diff;
- архитектурные границы соблюдены;
- сгенерированные файлы согласованы;
- все **относящиеся к задаче** локальные проверки выполнены;
- обязательные проверки `Python`, `Windows`, `Security` успешны на точной верхушке ветки;
- на точной верхушке ветки отсутствуют устаревшие параллельные процессы сбора свидетельств;
- упавшие проверки исправлены и повторены в затронутой области;
- полный набор тестов не повторялся без существенного изменения или диагностической причины;
- сканирование секретов выполнено по итоговому diff, относящемуся к задаче;
- самостоятельная состязательная проверка Codex завершена;
- явно запрошенные или обязательные внешние проверки обработаны;
- незапрошенный CodeRabbit остаётся в состоянии `NOT_RUN`, а не считается ограничением;
- проверка безопасности завершена в требуемом объёме;
- открытые блокирующие обсуждения ревью отсутствуют;
- документация обновлена;
- черновой PR создан или обновлён и содержит актуальные область изменений, base SHA, проверки и ограничения;
- PR ожидает финального пользовательского ревью;
- дальнейший жизненный цикл Git/PR определяется только `GIT-WORKFLOW.md`;
- ограничения перечислены;
- от пользователя не требуется рутинных технических действий.

### После подтверждённого слияния

Для уже слитой задачи дополнительно обязательны:

- проверка фактического SHA слияния;
- относящиеся к изменению проверки после слияния;
- подтверждение отсутствия новой регрессии в затронутой области.

Правила разрешения слияния и очистки принадлежат `GIT-WORKFLOW.md`.
