# Инструменты Python и внешние интеграции

## Назначение

Документ описывает **текущие** инструменты Python AzurPilot, принадлежащие
репозиторию, и их устойчивые границы. Это не дорожная карта миграции и не журнал
предыдущих задач.

При споре сначала проверять текущий код, ближайшие тесты и сгенерированные
контракты. Текущие PR, SHA ветки, локальные пути конкретной машины, состояние
цикла проверки и планы будущей реализации сюда не записываются.

## 1. Текущие владельцы

| Область | Текущий владелец | Инвариант |
|---|---|---|
| CLI | `azurpilot.cli` | разбор аргументов и формирование вывода отделены от логики служб; импорт не запускает операции |
| Типизированная модель результата | `azurpilot.tooling.contracts` | закрытые модели Pydantic, стабильные коды результата, состояния и причины, ограниченный объём свидетельств |
| Примитивы репозитория и процессов | `azurpilot.tooling` | точная идентичность, подтверждённое владение путём и процессом, ограниченные операции, отказ при неоднозначности |
| Жизненный цикл, сборка и восстановление | соответствующие службы в `azurpilot.tooling` | CLI служит адаптером; платформенно-зависимое поведение не дублируется в средстве вывода |
| Внешние интеграции | `azurpilot.integrations` | прямые типизированные адаптеры, ограниченная граница учётных данных и свидетельств |
| Состояние и совместимость MCP | инструменты Python и существующие проверки контрактов MCP | состояние исходников не выдаётся за фактическую регистрацию клиента |
| Пути совместимости Windows и оператора | проектные сценарии и модули PowerShell | не удаляются без доказанной эквивалентности и миграции вызывающих компонентов |

Пакет `azurpilot/` содержит инструменты и прикладную логику и не становится
владельцем игрового поведения. `alas.py`, `gui.py`, `module/application`,
`module/device`, боевые режимы, карты, кампании и другие продуктовые слои
сохраняют свои границы.

## 2. Контракт CLI

Установленная точка входа `azur` ведёт в `azurpilot.cli:main`. Текущая
реализация использует `argparse` и Rich; это описание существующей реализации,
а не предложение выбрать такой фреймворк в будущем.

CLI имеет два режима представления:

- человекочитаемый вывод — краткий интерфейс терминала;
- `--json` — ровно один закрытый машиночитаемый результирующий конверт.

Rich/ANSI и индикатор выполнения не меняют схему JSON. Слой служб не зависит от
средства вывода в терминале, а тесты и MCP не должны разбирать человекочитаемый
вывод как машинный контракт.

Команда, привязанная к проекту, не угадывает идентичность репозитория по случайному
текущему каталогу, если её нельзя подтвердить. Источник явной настройки или
установки проверяется; при неоднозначности возвращается типизированная ошибка.

### Обязательная граница операторских команд

Если возможность проекта уже представлена через установленный `azur` и
PATH текущей оболочки её подтверждает, действие оператора вызывается только
буквальной командой `azur ...`. `uv run ... azur`, `uv run python -m
azurpilot`, `python -m azurpilot`, `.venv/.../azur`, абсолютный путь к
`azur.exe` и обёртки PowerShell/cmd обходят установленный путь операторской
команды и запрещены. Отсутствие `azur` — типизированное состояние
`unavailable`/`precondition`, а не разрешение использовать запасной путь. `uv`
остаётся допустимым для управления зависимостями, начальной настройки,
тестирования и сборки, если эти действия не представлены операторской
возможностью проекта.

## 3. Типизированные результаты и свидетельства

`ToolingResult[TDetails, TEvidence]` и DTO конкретных операций — каноническая модель
между службой, выводом CLI в JSON и тестами.

Постоянные правила:

- схема закрытая; произвольный `dict[str, Any]` не используется как публичный
  контракт результата;
- сведения о результате и свидетельства ограничены по размеру;
- исходные данные провайдера, полные журналы, токены, файлы cookie, URL с учётными
  данными и личные пути не сериализуются;
- состояния `success`, `failure`, `unsupported`, `unavailable` и
  `not-configured` различаются типизированными кодами состояния и причины, когда
  этого требует контракт операции;
- тайм-аут или неизвестный результат внешнего изменения не считаются успехом
  по предположению;
- диагностическая команда только для чтения не получает скрытый запасной путь,
  который меняет состояние.

## 4. Свидетельства Git и публикация агентом

`GitClient` — минимальная граница только для чтения для диагностики,
анализа изменений исходников MCP и Semgrep: HEAD, состояние, добавленные в
индекс/изменённые пути, объекты Git и идентичность репозитория. Внутренние средства
инструментов Python используют Git только как источник свидетельств. Публичный
`azur` не изменяет Git и не публикует PR.

Порядок работы с Git/PR автоматически маршрутизируется к
[azurpilot-git-workflow](../../.agents/skills/azurpilot-git-workflow/SKILL.md).
Процедура напрямую использует системные `git`, `gh` и доступное структурированное
чтение GitHub через MCP. Python не выполняет commit/push, не формирует текст и
представление PR и не восстанавливает процесс публикации. Правила заданы в
`GIT-WORKFLOW.md`, проверки — в `08-VERIFICATION.md`.

## 6. Внешние интеграции

Точный каталог интеграций не дублируется в документации: канонические имена
берутся из `IntegrationName`, а порядок — из `ADAPTER_ORDER`.
`IntegrationRegistry` должен соответствовать этим источникам.

Интеграции реализованы с помощью прямых типизированных адаптеров. Docker MCP
Toolkit/Gateway и универсальный прокси MCP не входят в критический путь и не
служат запасным источником регистрации.

Общие правила:

- учётные данные пользователя или машины поступают из разрешённой внешней
  конфигурации или переменных среды и не попадают в отслеживаемые исходники;
- операции `status`/`doctor`/`read` имеют ограниченный объём;
- изменение через провайдера разрешено, только если конкретные адаптер и контракт
  операции явно его поддерживают;
- вывод провайдера приводится к ограниченному типизированному свидетельству;
- отсутствие внешней возможности не маскируется синтетическим успехом.

### Semgrep

Semgrep запускается только с явно заданным набором входных путей: добавленными в
индекс, изменёнными или указанными непосредственно, как требует контракт
команды. Сканирование всего репозитория не используется как неявное поведение
по умолчанию. Находки нормализуются, а путь должен оставаться внутри проверенного
корневого каталога.

### Grafana и Docker Hub

Обе интеграции используют общие долгоживущие службы Streamable HTTP, которыми
владеет Compose-проект `azurpilot-infrastructure` (профиль
`external-mcp`): `grafana-mcp` только на `127.0.0.1:8777`, `dockerhub-mcp` только
на `127.0.0.1:8778`. Конечная точка берётся только из подтверждённого
типизированного контракта; нельзя безусловно подставлять `host.docker.internal`
или угадывать адрес, а публикация не через loopback отклоняется.

Аутентификация клиента и учётные данные провайдера относятся к разным контурам.
Клиент предъявляет токен из `AZURPILOT_GRAFANA_MCP_CALLER_TOKEN` или
`AZURPILOT_DOCKER_HUB_MCP_CALLER_TOKEN` (Compose читает его из `.env`, а
MCP-клиент — из переменных среды своего процесса); учётные данные провайдера
остаются внутри Compose.
Третья общая служба — `github-mcp` на `127.0.0.1:8779`: идентичность GitHub
предъявляет вызывающий клиент, а провайдер запускается с серверным параметром
`--read-only` и точным `--tools`, включающим восемь инструментов только для
чтения. Готовность подтверждает принадлежащая репозиторию проверка loopback
(`401`, допускается `403`), а не проверка состояния контейнера. Репозиторий не
регистрирует клиент GitHub: подписка на этот маршрут настраивается локально
оператором, а команды проекта — `azur integrations shared-mcp
status|start|stop`.
Список разрешённых инструментов остаётся только для чтения, изменяющие состояние
инструменты блокируются; Grafana дополнительно ограничена на стороне сервера
(`--disable-write`, `--disable-api`, ограниченные категории), а доступ только для
чтения к Docker Hub обеспечивают PAT с ограниченными правами и типизированный
список разрешений. Жизненным циклом владеет Compose, операторская граница —
буквальная команда `azur integrations shared-mcp status|start|stop`.

### Context7 и Docker Docs

Используют прямой адаптер HTTP/MCP с ограниченным обнаружением и числом вызовов.
Наличие анонимного режима или режима с учётными данными определяется адаптером и
конфигурацией, а не зашитым в код секретом.

### CodeRabbit как навык репозитория

CodeRabbit не входит в каталог `IntegrationName`, `IntegrationRegistry` и
публичный интерфейс CLI `azur integrations`. Это средство проверки для
разработки, правила работы с которым принадлежат навыку репозитория
`.agents/skills/azurpilot-coderabbit-review/`.

Навык напрямую вызывает установленный системный CodeRabbit CLI, проверяет
фактический интерфейс текущей версии и независимо разбирает замечания.
Репозиторий не создаёт для CodeRabbit отдельный адаптер, машину состояний,
постоянное состояние проверки, манифест сортировки замечаний или список задач.
`.coderabbit.yaml` остаётся конфигурацией самого CodeRabbit.

Правила работы с Git заданы в `GIT-WORKFLOW.md`, а общая матрица проверок — в
`08-VERIFICATION.md`; навык CodeRabbit их не дублирует.

## 7. Граница MCP

Dev MCP и Game MCP остаются отдельными продуктами:

- `module.dev_mcp` — граница среды разработки: среда выполнения, Smoke,
  свидетельства и управление;
- `module.game_mcp` — граница чтения игрового состояния и управления игрой;
- `module.mcp_shared` — нейтральный общий код аутентифицированного транспорта и
  протокола, но не новый владелец продукта.

Канонические источники версий и совместимости находятся в метаданных проекта и
производных файлах совместимости плагина. Не копировать изменяемые таблицы версий
и хешей в контекст.

Диагностика MCP должна различать:

- отслеживаемую конфигурацию исходников;
- наблюдаемую локально среду выполнения;
- снимок плагина и исходников;
- фактическую регистрацию клиента или сеанса, если для неё есть достоверные
  свидетельства.

Нельзя объявлять фактическую регистрацию «готовой» только потому, что
`.codex/config.toml` корректен.

После фиксации соответствующего набора исходников один вызов
`azur mcp sync --base <exact-base-sha>` определяет фактическое влияние и
возвращает итоговый статус
`NO_CHANGES` или `SYNCED`. При наличии изменений операция пересчитывает
совместимость относительно точной базовой ревизии и варианта, записывает
канонический комплект и производные файлы, восстанавливает только принадлежащую
проекту устаревшую среду, проверяет готовность и выполняет приёмку новым
клиентом. Текущий внешний сеанс Codex не является постусловием; автоматическая
перезагрузка не предполагается. `impact`, `status`, `reconcile`, `start`,
`stop`, `restart` и `accept` остаются командами диагностики и
администрирования; не объединяй их в обычный автомат состояний. Любое изменение
набора исходников MCP требует повторной синхронизации.

Мост Windows имеет отдельный узкий операторский интерфейс
`azur mcp bridge status|configure|start|stop|restart|accept`, принадлежащий
`McpService`. `configure --stdin-token` безопасно сохраняет отдельный токен
вызывающего клиента из stdin в защищённый `.env`; клиент Linux читает то же
значение тем же каноническим владельцем во время подготовки генерации и получает
его только через окружение процесса.
`status` возвращает закрытый `McpBridgeStatusDetails`: состояние моста
(`ready`, `stale`, `stopped`, `unknown`, `conflict`), конечную точку и фиксированные
маршруты, состояние аутентификации клиента (`configured`, `unavailable`,
`unknown`), подтверждение владения процессом, PID, состояние и идентичность
исходников обеих серверных частей. Для каждой серверной части состояние может быть `ready`, `stale`,
`stopped`, `unavailable`, `unknown` или `conflict`. Результат не содержит
значений учётных данных или локальных путей. `start`, `stop` и `restart`
управляют только процессом моста, владение которым подтверждено; они не
перезапускают серверные части Dev/Game. Для запуска нужно настроить учётные данные
клиента в `.env` проекта.

`accept` создаёт новые MCP-сеансы через оба маршрута моста и выполняет
ограниченные проверки только для чтения: `dev_get_contract`,
`dev_list_smoke_capabilities`, `game_get_contract` и `game_list_profiles`.
Команду выполняют только из чистой рабочей копии. Результат имеет состояние
`READY`, `INCOMPATIBLE`, `UNAVAILABLE` или `UNKNOWN`. Эта приёмка на Windows
проверяет сам мост и не заменяет приёмку клиента Linux.

Клиентской границей DeepSeek Harness владеет `azurpilot.tooling.dsh`:
`azur dsh prepare` собирает генерацию сессии и до старта Harness выполняет приёмку
обоих маршрутов тем же каноническим клиентом, `azur dsh launch` доводит сессию до
подтверждённой активации клиентов и наблюдает её как супервизор, а
`azur dsh verify` сверяет текущий checkout с генерацией работающей сессии.
Ожидаемую идентичность источника вычисляет общий владелец
`azurpilot.tooling.mcp_source_identity`; значения `/identity/dev` и
`/identity/game` остаются только диагностикой. Генерация живёт только в окружении
процесса Harness, поэтому буквальный токен и изменяемая идентичность не попадают
ни в профиль Harness, ни в общий файл. Обычная сессия DeepSeek Harness без этого
overlay от моста не зависит.

Запуск продукта закрыт контрактом владельца: точный pin `0.1.7-rc.2` держит
список обязательных entry в константе `dsh-app-boot`, поэтому `failOnStartupError`
и `apply()`, завершающийся отказом, не делают запись обязательной — неактивная
запись даёт предупреждение. `launch` разбирает эффективную композицию из `--dump-config` и считает запуск
успешным только по аттестации с `guard_installed: true` и `verification: ready`.
Проверка семантическая, а её отказ — предусловие (код выхода 20): отдельный код в
`ResultCode` не заводится, потому что `result.py` входит в общий набор MCP.

Страж `azurpilot/dsh/azurpilot-bridge-guard.mjs` регистрируется на монотонной
границе `ctx.tools.guard()`: переставляемый `tools/pre-execute` позволил бы более
позднему слушателю превратить подтверждённое расхождение в разрешение. Владельцем
проверки остаётся `azur dsh verify`; страж обновляет вердикт фоновым watchdog и
читает устоявшееся состояние, поэтому вызов инструмента проверку не запускает, а
отмена сессии не оставляет процесс. Неизвестное, устаревшее и недоступное
состояние означают запрет. Внутренние токены Dev/Game из внешнего окружения в
дочерний процесс не передаются: имена берутся у владельца
`MCP_LOCAL_TOKEN_ENVIRONMENT_KEYS`.

Для необязательной проверки регистрации Codex используй [единый контракт
продолжения между задачами](../../.agents/skills/azurpilot-repository-development/references/cross-thread-task-delegation.md);
она не заменяет обязательную проверку нового клиента MCP.

## 8. Базовый кроссплатформенный контракт

Базовые инструменты Python и CLI сохраняют одинаковую семантическую модель для
Windows, Linux и macOS: DTO, коды причин, контракт JSON, идентичность репозитория,
структурированный запуск процессов и ограниченные примитивы файловой системы и
Git.

Внешние и продуктовые возможности зависят от среды:

- ярлык WSL/COM доступен только в Windows;
- конкретная серверная часть эмулятора или устройства требует отдельного подтверждения;
- доступность Docker/PostgreSQL зависит от настроенной среды выполнения;
- среда проверки CodeRabbit зависит от подтверждённых системного адаптера и среды
  выполнения, а также точной идентичности процесса.

Запуск основного CLI в ОС сам по себе не доказывает поддержку устройства,
эмулятора или внешнего провайдера в этой ОС.

## 9. Граница совместимости PowerShell

В поддерживаемой области продукта владельцем команд Start/Stop/Repair/Build являются
инструменты Python. PowerShell остаётся только связующим средством запуска;
старые сценарии оболочки допустимы лишь для внешних системных подключаемых
компонентов и настройки CI, но не как второй операторский путь проекта. Удаление
старого пути требует одновременно:

- эквивалентного поведения при успехе, ошибке и восстановлении;
- точных свидетельств владения, путей, процессов и Git;
- миграции вызывающих компонентов, документации, ярлыков и установщиков;
- актуальных тестов и проверок CI на затронутых ОС;
- отдельного решения об удалении, а не вывода «Python уже умеет похожую команду».

Подключаемые сценарии PostgreSQL, входящие в образ или контейнер, не считаются
старыми обёртками узла только потому, что написаны на языке командной оболочки.

## 10. Граница безопасности

Инструменты не должны:

- печатать секреты или полные URL с учётными данными;
- сериализовать произвольные журналы провайдера в JSON-свидетельства;
- читать произвольные файлы за пределами проверенного корневого каталога;
- останавливать процесс по PID, порту или имени без свидетельств владения;
- выполнять произвольный код командной оболочки или динамическую оценку через `eval`
  в обход типизированного адаптера;
- автоматически исправлять неоднозначное состояние операцией изменения;
- переносить пользовательские секреты или конфигурацию в рабочую копию для проверки
  или одноразовой работы.

## 11. Маршрутизация проверок

Проверки выбираются с учётом изменённой области.

Для контракта основного CLI и инструментов Python:

- проверка синтаксиса, компиляция и статический анализ кода;
- целевые проверки контрактов и интеграций;
- вызов команды в человекочитаемом режиме;
- соответствующий вызов с `--json`, возвращающий один закрытый результирующий конверт;
- проверка платформы, если затронут системный адаптер.

Для внешних интеграций:

- тесты соответствующего адаптера или службы;
- `dev_tools/integration_contract_gate.py`;
- ограниченная проверка в рабочей среде или у провайдера, только если доступны
  необходимые условия и такая операция действительно входит в задачу.

Для изменений исходников и совместимости MCP дополнительно применяются
существующая проверка совместимости MCP и проверка производных метаданных.
`azur mcp sync --base` завершает этот цикл одним итоговым результатом:
`NO_CHANGES` или `SYNCED`; успешный
`SYNCED` подтверждает `source_reconciled`, `runtime_ready` и приёмку новым
клиентом. Синхронизация проверяет только доступную принадлежащую проекту среду
выполнения и не утверждает, что текущий внешний сеанс перечитал снимок плагина.
В ходе `sync` новый клиент запускается на изменённом варианте, а совпадение
дайджестов набора исходников MCP проверяется до и после приёмки; отдельная команда
`azur mcp accept` отказывает при незафиксированных изменениях рабочей копии.

Для изменений инструментов Windows запускаются проверки CLI Python,
жизненного цикла, ярлыков, восстановления и сборки. PowerShell остаётся только
связующим средством запуска и не является рабочей реализацией операторских команд.

Общие критерии готовности находятся в `08-VERIFICATION.md`.

## 12. Что не следует хранить здесь

Не добавлять обратно:

- номер временного этапа или состояние отдельной итерации задачи;
- исходное задание пользователя и историю выбора фреймворка;
- предлагаемую будущую структуру каталогов рядом с уже действующей;
- текущие PR, ветку, SHA или запуск CI;
- буквальные пользовательские пути и пути конкретной машины;
- таблицы версий, уже генерируемые из канонического источника;
- обещание возможности, которой ещё нет в коде;
- привязку обязательной итоговой проверки к конкретной модели или версии.

Если появляется новый устойчивый владелец или граница, обнови соответствующий
раздел и удали устаревшую формулировку, не накапливая рядом временные слои.
