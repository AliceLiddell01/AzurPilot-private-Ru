# Оркестрация субагентов

Этот документ — единственный владелец политики использования субагентов Codex
в рамках проекта. Он регулирует делегирование и внутреннюю независимую проверку;
жизненным циклом Git владеет `GIT-WORKFLOW.md`, а общей матрицей проверок —
`08-VERIFICATION.md`.

## Принципы

- Делегируй конкретный независимый вопрос с ожидаемым проверяемым результатом,
  а не расплывчатое «изучи модуль».
- Субагенты по умолчанию собирают факты. Корневой агент определяет границы задачи
  и архитектуру, выполняет общие изменения, объединяет результаты, завершает
  подготовку сгенерированных исходников и владеет Git, MCP и публикацией.
- Не дели связанные изменения продуктового кода между несколькими субагентами.
  Роли проекта настроены с `sandbox_mode = "read-only"`, но это только
  конфигурационное намерение: в Multi-Agent V2 эффективный профиль разрешений
  дочернего потока повторно задаётся активным профилем родительского хода. Поэтому
  `read-only` в файле TOML роли не гарантирует изоляцию дочернего потока, если у
  родителя есть права на запись. Роли обязаны соблюдать запреты на изменение файлов
  и создание собственных субагентов как инструкции проекта; корневой агент остаётся
  единственным владельцем общих изменений.
- В Codex V2 поле выбора `agent_type` формируется из непустого набора загруженных
  `agent_roles`; роли из доверенной проектной папки `.codex/agents/*.toml`
  обнаруживаются автоматически. Параметр `hide_spawn_agent_metadata` на выбор роли
  не влияет.
- Обычная структура делегации в проекте плоская. Запрет на вложенную делегацию —
  политика проекта и обязательное указание в `developer_instructions`, а не
  техническая гарантия V2: механизм V2 может предоставлять дочернему потоку инструменты
  делегации. `agents.max_depth` относится к V1 и не ограничивает V2; не добавляй его
  как фиктивную защиту.
- Используй параллелизм, когда направления действительно независимы. Малой задаче
  может хватить нуля или одного субагента; предел параллельности — потолок, а не цель.
- Пока субагенты работают, корневой агент продвигает независимые части задачи.
  После их ответа используй результаты как подтверждающие материалы, выборочно
  проверь критические факты, разреши расхождения по коду, тестам и контрактам и
  не повторяй всё исследование без нового вопроса.

## Рабочие волны

Для существенной работы или изменений, затрагивающих несколько подсистем, используй
последовательность:

```text
независимое исследование
        ↓
синтез и реализация корневым агентом
        ↓
существенный вариант изменений
        ↓
свежая независимая волна проверки
        ↓
разбор результатов и исправления корневым агентом
```

Волна проверки оценивает фактический набор изменений. В неё входят новые потоки
агентов, не участвовавшие в первоначальном исследовании или
реализации. Выбирай проверяющих по затронутой границе; для PR с изменённым
человекочитаемым текстом обязательно подключай `localization_reviewer`. Он
проверяет смысл всего текста изменённых PR-файлов, а не только новых строк.
Существующий `runtime_russianization_audit` остаётся отдельной автоматической
проверкой.

Не запускай такую волну механически для любого малого изменения. После
существенной правки варианта изменений пересмотри только выводы тех проверяющих,
чья область затронута.

## Роли проекта

Используй узкую роль по вопросу задачи:

| Роль | Вопрос |
|---|---|
| `architecture_scout` | Кто владеет поведением, каков ограниченный путь вызовов, где проходят текущие границы абстракций и какие действуют инварианты, контракты и тесты? |
| `implementation_investigator` | В чём первопричина, какие пути жизненного цикла, состояния, параллельности и ошибок затронуты, где минимальные точки изменения и какие есть риски? |
| `regression_analyst` | Какие существующие тесты защищают поведение, какие реалистичные пути регрессии возможны и какого целевого покрытия не хватает? |
| `adversarial_reviewer` | Какие доказуемые ошибки корректности, гонки, нарушения владения, небезопасные пути, ошибки восстановления или регрессии есть в изменениях? |
| `contract_consistency` | Есть ли расхождения по смыслу между кодом, конфигурацией/схемой/CLI, документацией/контекстом/навыками, тестами и сгенерированными исходниками? |
| `localization_reviewer` | Остался ли в изменённых файлах человекочитаемый иностранный текст, который нужно перевести на русский? |

Подробные инструкции ролей находятся в `.codex/agents/*.toml`; не копируй их
в `AGENTS.md`, навык или матрицу проверок.

## Общие правила ролей

Каждая роль:

- наследует параметры модели и рассуждения из `.codex/config.toml`; корневой агент
  не переопределяет их без явного требования задачи;
- по политике проекта действует только в режиме чтения, не изменяет репозиторий и
  не выполняет Git, MCP, доставку, PR или другие операции жизненного цикла;
  фактический профиль разрешений определяется активным родительским ходом;
- не создаёт вложенных субагентов;
- возвращает краткие проверяемые выводы с конкретными путями, символами,
  контрактами или тестами, отделяя факты от предположений.

Определения ролей не задают собственные модель или глубину рассуждения.
